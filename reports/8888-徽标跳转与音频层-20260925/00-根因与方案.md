## 一、问题 1a：徽标有「内切镜」、描述里没有

### 1.1 机制（为什么必然发生）

**① 徽标（`summary`）是模型自由文本，唯一写闸只查「键序」不查「内容一致性」。**

- 字段定义：`src/video_agent/tools/storyboard_tools.py:133` —— 要求「须与 desc 镜头结构一致」，但这是**散文要求**，无任何机器校验。
- 写入闸：同文件 `:138-157` `_desc_before_summary` —— **只校验入参 JSON 里 `desc` 键必须排在 `summary` 键之前**，注释原文：「只查字段顺序、**不看内容**、不碰格式红线」。意图是「先写完整 desc、再据其提炼徽标」，但顺序合规 ≠ 内容一致。
- 缺失拒收：`:269-277` 只挡「summary 为空」。
⇒ **徽标与 desc 在平台侧是两条互不校验的通道**，一致性完全靠模型自觉。

**② desc 的格式模板里根本没有「内切镜」的槽位。**

- Skill 规定的 desc 三件套（`data/skills/AI-短剧一站式生成/SKILL.md:77-95`）：**场景** + **人物动作与对白** + **分镜语法三件套（景别/机位/运镜）** + 开头的**空间锚点卡**。**没有任何一处要求逐条列出内切镜**。
- 「内切镜」一词在该 Skill 里只出现在两个**别处**：`:73`（批次拆分规则「单 shot 内切镜数量建议 2—6 个」）与 `:104`（Storyboard 自检清单「每个内切镜是否在景别建议时长内」）、`:153-164`（`write_media_prompt` 的时长估算表）。
⇒ 模型被要求「写完整镜头设计」，但模板没给它写内切镜的地方；它把内切镜**记在徽标里**（徽标问的就是「镜头结构摘要」），desc 里则按模板用**一行的「分镜语法：景别=A→B→C；机位=…；运镜=…」**把多镜带过。

### 1.2 实证（本仓真实数据）

**8888（10 镜）**：徽标 10/10 含「内切镜」，desc **0/10** 含「内切」；desc 的内切信息被压进单行「分镜语法」：

| 镜 | 徽标（summary） | desc 尾部（唯一形态载体） |
|---|---|---|
| 0 | 含3个内切镜：双人苏醒→飘向舷窗→舷窗木星（约10s） | 分镜语法：景别=中全景（双人+舷窗同框）→中景；机位=平视；运镜=缓慢推进。 |
| 8 | 含5个内切镜：灯光调暗全景→研究员报告→手穿薄膜→'它什么也不做'→白Ice回应（约15s） | 分镜语法：景别=全景（…）→特写（…）→近景胸像（…）；机位=平视+过肩；运镜=固定+缓慢推进。 |

**6666（14 镜，09-24 跑的同一 Skill、同剧本）**：desc **14/14 逐条枚举内切镜**，形态为
`1) 内切·全景（平视·缓慢推近）：…` / `2) 内切·大特写（平视·固定）：…`
（`shots_report.txt` L22-25）。**徽标与 desc 在这里是自洽的。**

⇒ **同一 Skill、同一平台、隔一天两跑，desc 形态完全不同** —— 这正是用户说的「描述不稳定」。它不是某次提交引入的回归，而是**采样波动 + 无模板槽位约束**：desc 的自由度太大，模型每次自组织一种排版。此定性与 `CHANGELOG.md` 2026-09-24 条一致（「复述行 = deepseek-v4-flash 逐次采样的合规表态波动，**不赌模型脾气**」）。

**回喂面也无纠偏**：`src/video_agent/state/context_builder.py:125-140` 把 `summary` 与 `desc` **一并注入**模型每轮状态（注释：「模型每轮看见自己的写入侧承诺，跨轮维持 desc 与徽标自洽」）——跨轮自洽靠的是「模型看得见」，同样不是校验。

### 1.3 徽标「流程」字样：全库 0 命中，不可复现

## 二、问题 2：引用 chip 点击跳转不稳定（已定案，双因）

（完整取证见 `.tmp_probe/refs_jump_bug_report.md`，142 行，含全部 file:line 引文。）

### 2.1 主因：逐字比对 vs 裸名存储

`src/web/stores/studio/ui.ts:129-134`：

```ts
jumpToElementByTitle(title: string) {
  const el = state.keyElements.find((k) => k.title === title || k.id === title);
  if (!el) { showToast(`未找到关键元素「${title}」`, 'warning'); return; }
```

- 落盘关键元素标题 **14/14 恒带 `Element_` 前缀**（写口 `storyboard_ops.py:257-263 normalize_group_title` 幂等补前缀）。
- 而 `shotRefs` **47 条里 43 条存裸名**（91.5%）。
- ⇒ **91.5% 的 chip 点击必然落到 toast**。

**「有时灵有时不灵」的精确解释**：完全由该条引用**写入时的字面形态**决定。三源合并 `storyboard_ops.py:717-730 merge_shot_refs` 中，② `[令牌]` 源与 ③ 裸名提及源返回的都是**带前缀组标题**，只有 ① 显式 `shot_refs` **原样透传**。实证同一元素的两种形态并存：

| 元素 `白色薄片` 出现的镜 | 存储形态 | 能否跳转 |
|---|---|---|
| `Shot_程心追问打击…` | `Element_白色薄片` | ✅ |
| `Shot_太空艇抵近目标…` / `Shot_机械臂伸向薄膜…` / `Shot_瓦西里戴手套…` / `Shot_二十多小时过去…` | `白色薄片` | ❌ |

**逐镜可跳统计**：10/10 分镜都含至少一个点不动的 chip；可见 chip 47 个 → 可跳 **4（8.5%）** / 必失败 **43（91.5%）**。
**对照**：同一份 state 走后端 `find_ref_group`（canonical）⇒ **47/47 全命中**。

### 2.2 次因（独立）：DOM 缺失时静默丢弃

`StoryboardView.tsx:108-131`：跳转落地靠「双 `requestAnimationFrame` 后查 DOM」，查不到就 `if (!target) return;`（`:123`）**无任何提示**。而该组件只在 `leftTab === 'storyboard'` 时挂载（`LeftPanel.tsx:49`），左栏又被 `AgentLayout.tsx:62` 的收起 `<Show>` 包着。⇒ 停在「未归类素材」页签或左栏收起时，store 状态照样更新、**滚动与闪烁静默丢弃**。这就是「有时弹未找到、有时毫无反应」两种现象并存的原因。

### 2.3 单一实现违规（本次的技术性质）

canonical 助手全仓只有一份 `desc-ref-utils.ts:32 stripTypePrefix`，且**展示层（`ShotRefsChips.tsx:20`）、缩略图（`desc-ref-utils.ts:107-111`）、后端读口（`storyboard_ops.py:216-254`）全都 canonical，唯独点击链逐字**。后端注释 `storyboard_ops.py:198-213` 早已把同类缺陷定性为「同一条引用链各处各写一遍比对式」（事故 4444/P0-A 同源）。

**旁证（更彻底的一条）**：正文内联块跳转 `ShotDescEditor.tsx:145` 传 `chip.dataset.name`，而该 dataset 是**裸名**（`desc-ref-utils.ts:99-101`）⇒ **100% 失败**。

**测试为什么没抓到（假绿）**：`studio.test.ts:8-15` 的 `title: '元素ke2'` 跳 `'元素ke2'`、`ShotRefsChips.test.tsx` 用裸 ref、`ShotDescEditor.test.tsx` 用裸 `'程心'` —— 夹具的元素标题**一律裸名**，恰好与裸名 ref 逐字相等，永远测不出前缀问题；也没有任何用例覆盖「左栏未挂载 / DOM 缺失」路径。

## 三、问题 3：音频层在设计期建了卡（已定案，三重叠加）

（完整取证见 `.tmp_probe/audio_layer_report.md`，178 行，含全部 file:line 引文与可复跑探针。）

### 3.1 平台放行：闸机只看 mediaType，不区分 audioType

- 白名单唯一源 `src/video_agent/core/subagent.py:195-197`：`STAGE_CARD_MEDIA = {"storyboard_design": {"audio", "video"}}`。
  设计意图注释 `:187-194` 明写 audio 这一格的本意是「← key_elements 的角色音色卡（`key_element_audio`）」，但**实现是 mediaType 维度，没有细分**。
- 闸机 `src/video_agent/core/fc_gates.py:450-467`：`media = ops_infer_media_type(draft); if media in allowed: return None` —— **完全不读 `audioType`**。
- **实测**：BGM 卡 PASS / 旁白卡 PASS / 音色卡 PASS / 「只给 audioType=bgm」PASS / 图像卡 REJECT。
- 该行为**被回归测试钉死**：`tests/unit/test_production_prune.py:309-311` 断言 `{"audioType": "bgm"}` **放行**（该断言的本意是修 4444/P1-5「只填 audioType 被误判为 image」，副产品是把 bgm 一起放行了）。

### 3.2 字段契约鼓励建卡（模型不是违规方）

模型可见文本里**没有一句**说「设计期音频只写描述」；相反：

- `storyboard_tools.py:40-41`：`音频卡用 audioType 声明种类（voice/bgm/narration/sfx/dialogue/foley；voice = 角色音色卡…）` —— 把 bgm/narration 与 voice **并列**。
- `storyboard_tools.py:48-50`：`**mediaType 与 audioType 配套**：音频卡两个都标…`
- `storyboard_ops.py:42`：`AUDIO_TYPES` 含 bgm/narration，注释直说「属**草稿**字段（音频种类是卡的属性）」。
- `storyboard_ops.py:84-96 matrix_contract_line` 渲染进 `group_type` 描述：`audio（该类目可放：音频；可出：音频）`。

⇒ 8888 三张 `audioType=bgm` 卡是**照契约执行**，不是越权。真实产物：3 组各 1 张卡，卡面 label `BGM-01 末日序曲`、`tag: Agent`、带完整中文 prompt（46s/42s/37s 配器设计）。

### 3.3 Skill 被改坏 —— 本项目引入了 flova 从未有的「按草稿配置」

| | flova 一手快照 | 本仓现文 |
|---|---|---|
| BGM | `使用 **text_to_instrumental**，推荐模型：**Suno 5**` | `由系统音频生成通道（text_to_instrumental 纯音乐通道）**按草稿配置产出**，模型与分辨率按全局设置的默认渠道填写` |
| 旁白 | `使用 **text to narration**，推荐模型：**ElevenLabs v3**` | `由系统音频生成通道（text_to_narration 旁白通道）**按草稿配置产出**，…` |

- **「按草稿配置产出」这句预设了草稿卡存在**，是 flova 全篇没有的语义（flova 快照全文无「草稿」二字）。
- 引入点：`git log -S '按草稿配置'` → commit **`7bb5a672`**（"整改批2.1b 幻影工具名清偿"）—— 该批唯一目的是删幻影工具名 `audio_generate`，**顺手新增了这条语义**。
- **无任何裁决留痕**：全仓 `docs/` + `CHANGELOG.md` grep「按草稿配置」= **0 命中**。
- 已扩散到 **3 个 Skill**：`AI-短剧一站式生成`（L146-147）、`人文纪录短片`（L106-107）、`视频拉片复刻`（L12 附近）。

### 3.4 两条同源静默失效（用户看到的空 = 两处不同缺陷）

1. **描述不进模型快照**：`src/video_agent/state/context_builder.py:161-182` 的音频分支只有 `title / timeRange / prompt_chars / drafts` —— **唯独音频类目缺 `desc` 键**（ke 在 `:106`、shot 在 `:140` 都有）。实测：模型看到的 audioItems 里 3 组 desc 全部缺失，只见 `prompt_chars: 0` + 1 张卡。
2. **前端描述位读错字段**：`src/web/components/left-panel/GroupCard.tsx:123`：`desc: (props.group as AudioGroup).prompt || ''` —— **读 `prompt` 不读 `desc`**（ke 分支 `:99` 才是 `g.desc`）。而 8888 三组 `desc` 有值（146/130/157 字）、`prompt` 全空 ⇒ 用户看到「双击添加描述...」。
   连带：`types/index.ts:138-144` 的 `AudioGroup` **没有 `desc` 字段**；`group.prompt` 的唯一写点是前端 `board-edit.ts:110`（`// audio 走 prompt`），**后端写点 = 0** ⇒ `prompt` 是「活字段但第二事实源」。

### 3.5 承接链缺口（删卡前必须先补，否则断链）

- 音频"生成"消费的是**卡片**而非组描述：`src/web/lib/generate-actions.ts:166-213` —— `if (!draft) { showToast('请先在左侧选中一个音频草稿卡片'…) }`，prompt 取 `draft.prompt`，结果**回写同卡**；`group.desc` 在该文件 **0 命中**。
- 后端**没有音频生成路由**：`src/video_agent/web/generation_channel.py:129` 直认「**当前版本无真实音频文件生成调用**」；音频生成 = 一次 chat 补全（文本规划）。
- **「描述 → 卡」目前没有落点**：可委派阶段只有 3 个（`subagent.py:116-120`），`audio_generate` **不在其中**；`storyboard_add_draft` 只在 `storyboard_design`（受 `{audio,video}` 限）与 `write_media_prompt`（**不受限**）授权。
⇒ **若只把 bgm 卡挡在设计期而不补承接，`generateAudio` 将永远早退、音频规划功能断链。**
