## 二、问题清单（逐条取证）

### P0-1 · `todo_write` 的 `items` 是悬空 `$ref`（新工具，本批引入）

**现象**：`todo_write` 在本次运行中**被调用 11 次，失败 7 次**，且失败是**三种不同的字段名猜测**：

| 时刻 | 模型猜的键 | 日志 |
|---|---|---|
| 18:30:16 附近（子代理1） | `{title, status}` | `todos.0.title: Extra inputs are not permitted` |
| 18:31:26 / 18:31:30（主代理） | `{text, status}` | `todos.0.text: Extra inputs are not permitted` |
| 18:34:52 / 18:41:48 / 18:44:03 | `{label, status}` | `todos.0.label: Extra inputs are not permitted` |
| 18:48:31 | `{item, status}` | `todos.0.item: Extra inputs are not permitted` |

**规范侧一切正确**——`prompts/shared/todo_write.md` 明确写了「状态取值：pending（未开始）、
in_progress（正在做）、completed（已完成）」「每次提交完整清单」；
`tests/unit/test_todo_write.py` 有 4 条断言锁定 `content`/`status`。
**模型照做也对**：它每次都用了**正确的中文状态值**（`"已完成"` 被拒时日志只报 content 一条）——
说明它读懂了描述里的状态枚举，**唯独不知道条目的键名**。

**根因（代码级，已复现）**：`src/video_agent/tools/manager.py:181-193`

```python
json_schema = schema_class.model_json_schema()
...
"parameters": {
    "type": "object",
    "properties": json_schema.get("properties", {}),   # ← 只取 properties
    "required":   json_schema.get("required", [])      # ← 与 required
}                                                       # ← $defs 被丢弃
```

`TodoWriteInput.todos` 是 `List[TodoItem]`（**唯一的嵌套 BaseModel**），
pydantic 把 `TodoItem` 放进 `$defs`、`items` 只留 `{"$ref": "#/$defs/TodoItem"}`。
丢 `$defs` 后，**下发内容里不含 `content`/`status` 任何一个字**：

```json
{"type":"object","properties":{"todos":{
   "items":{"$ref":"#/$defs/TodoItem"},"type":"array"}},"required":[]}
```

**实测影响面（25 个已注册工具逐个体检）**：

```
## 悬空 $ref 的工具（1 个）
- todo_write  -> 未定义引用: ['TodoItem']
```

**只有 `todo_write` 中招** —— 它是**本仓第一个、也是唯一一个**用嵌套 BaseModel 描述条目结构的工具。
其余 24 个工具要么属性是标量，要么把子结构写成 `Dict[str, Any]`（如 `storyboard_create_group.draft`、
`storyboard_patch_draft.patch`，子字段名放在 **description 文本**里），因此天然免疫。

**为什么测试没抓到**：`test_todo_write.py` 全部走 `ToolManager.invoke_tool(name, {...})`
**直接传 dict**——而 `invoke_tool` 用的是 `schema_class` 的 **pydantic 校验**（`$defs` 在 pydantic 内部完好），
**从不经过 `_full_schemas` 的下发路径**。测试测的是执行链路，缺陷在下发链路：**两条路各自正确，交汇处漏了**。

**为什么危害没有更大**：模型盲猜的键名（title/text/label/item）**不在** `TodoWriteInput.model_fields` 里，
被 `invoke_tool` 的未知字段闸先拦下（`manager.py:213`），**没走到 pydantic**，所以子项缺 `content`
的真实报错（`todos.0.content: Field required`）从未作为首因出现。同时 `content` 有
`Field(...)` 必填约束 + `error_code="validation"` + `retryable=False`，
**兜住了「静默丢弃」这条红线**（否则整表覆盖语义会静默清空清单）。**这是运气，不是设计。**

**代价**：7 次失败 × 一轮心智 + 反馈 token；且主代理每次**都要在同一轮重新提交整表**（整表覆盖语义），
多花了 5 轮 step 的往返。

### P1-3 · 「已连续失败 2 次」提示挂在每个批次成员上（措辞失真）

**现象**：同一次调用里，5 个**内容各不相同**的 shot 各自收到：

> `该工具已连续失败 2 次，同参重试大概率仍失败，不得再次重试；可向用户说明原因并给出替代选择。`

**取证**：`conv-1790159633` 的 seq55–59，5 条 `storyboard_create_group` 失败，第 2–5 条都带这句。

**根因**：`core/fc_tool_runner.py:817`

```python
self._tool_fail_counts[name] = self._tool_fail_counts.get(name, 0) + 1   # ← 按工具名计数
```

计数器是**按工具名**累计的，而提示文案（`core/fc_feedback.py:79`）说的是
**「该工具已连续失败 2 次」**。同批次里 5 个调用共用一个计数器，
第 2 个起的每个成员都被发了「你已失败 2 次」——**对第 2 个成员字面为真、对第 5 个成员极具误导**：
它们**不是同一个调用**，各自的 `sceneRefs` 问题也不同，本该各改各的。

**后果**：模型收到「不得再次重试」后确实**没再盲重试**（改了参数，行为正确），
但这条提示对「同批不同参」的场景语义错误——措辞失真虽没导致本次走错，
却是在用一句不准确的话去驱动模型的止损决策。
