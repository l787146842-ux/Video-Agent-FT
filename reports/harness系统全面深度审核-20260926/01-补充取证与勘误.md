## 一、对主报告的修正（勘误）

### 勘误 1：主报告「优点」表中的「状态增量注入」条目**不成立**

主报告在「维度 C：上下文与记忆工程 / C.1 做对了什么」中列了：

> ✅ 状态增量注入 | `planner.py:1191-1218`：`state_delta_enabled` 首轮全量基线，后续只推变化组（digest 未变绝不重复注入）

**该结论错误，予以撤回。** 复验证据链：

```python
# planner.py:215-217 —— digest 是【请求级】PlannerContext 实例字段
    # B 方案增量对账（state_delta_enabled）：上一轮的状态 digest/哈希
    _state_digest: Optional[Dict[str, Dict[str, str]]] = None
    _state_hash: str = ""

# web/chat_service.py:497 与 :880 —— PlannerContext 每请求新建（两处构造点）
    return PlannerContext(...)

# planner.py:1191-1200 —— 读取该字段
        if settings.state_delta_enabled:
            raw_state = self.state_manager.state_dict
            new_digests, new_hash, delta = state_delta_mod.compare_state(
                context._state_digest, context._state_hash, raw_state)

# state_delta.py:89-90 —— old_digests 为 None 即判 fresh
    if old_digests is None:
        return new_digests, new_hash, {"_fresh": True}

# state_delta.py:124-127 —— fresh 恒判有变化
def has_any_change(delta):
    if delta.get("_fresh"):
        return True
```

**结论**：`_state_digest` 恒为 `None`（每请求新建、无任何跨请求持久化写入点——`grep _state_digest` 全仓仅 `planner.py:216` 声明与 `:1194` 读取、`:1212` 写入同一方法内）⇒ `compare_state` 恒返回 `{"_fresh": True}` ⇒ `has_any_change` 恒 `True` ⇒ 恒走 `planner.py:1200-1206` 的**全量基线分支**，`build_delta_message`（`state_delta.py:135`）**生产永不可达**。

**同时确认反向后果**：`planner.py:1196-1198` 的「无变化即跳过」分支同样不可达，所以实际行为是**每轮全量注入状态 JSON**（实测最大项目状态 111,590 字节）。这使主报告「维度 C」的问题项 **C-2（状态全量重放）比原判更严重**——不存在任何生效的增量机制，`state_delta_enabled=True` 这个默认开关是**空转的**。

**测试面佐证**：`grep -r "state_delta|_state_digest|build_delta_message" tests/` → **0 命中**。即这套「B 方案增量对账」既无生产生效证据，也无任何测试覆盖。

**升级后的严重度**：high（原 C-2 记为「中」，现上调）。

## 二、新增发现（均已独立复验）

### 新增-1【blocker 级 · 但需精确表述】工作流「产物账本」整层未接线

> **勘误声明**：子代理原表述为「`commit_turn` 是死代码 / DecisionOpened、StageSucceeded 从未入账」。复验后**部分修正**：
> - ✅ 正确：`DecisionOpened` / `StageSucceeded` / `ArtifactCommitted` / `TurnCommitted` **在生产路径确实从不产生**。
> - ❌ 不精确：不能笼统称「`commit_turn` 是死代码」——`workflow_runtime.py:481` 的**实例方法** `WorkflowRuntime.commit_turn` 确为零调用（`grep '\.commit_turn\('` 全仓 0 命中），但**模块级函数** `turn_commit.commit_turn` 经 `WorkflowRuntime.resolve_decision`（`workflow_runtime.py:503`）**在产线可达**，并成功产生 `DecisionResolved`。

**复验证据**：

```python
# workflow_runtime.py:481-490 —— 实例方法：零调用者（grep 确认）
    def commit_turn(self, result: Any, **kwargs: Any) -> TurnCommit:
        commit = commit_turn(self.state_manager, result, skill=self.skill, **kwargs)
        run = sync_run(self.state, self.skill)
        ...

# workflow_runtime.py:492-520 —— resolve_decision 调【模块级】commit_turn（产线可达）
        commit = commit_turn(
            self.state_manager,
            TurnResult(..., timeline_events=[{
                "event_type": "DecisionResolved", ...}]),
            skill=self.skill, expected_version=int(run.get("run_version") or 0))

# web/chat_consume.py:102 —— resolve_decision 的真实调用点（活路径）
            workflow_runtime.WorkflowRuntime(svc, _sk).resolve_decision(
                _tok, str((pause_response or {}).get("value") or "confirm"))
```

**精确的失效范围**（`turn_commit.py:255-340` 逐段复验）：

| 事件 / 状态 | 产生条件 | 产线可达？ | 证据 |
|---|---|---|---|
| `DecisionResolved` | `resolve_decision` → `commit_turn` | ✅ **可达** | `chat_consume.py:102` |
| `DecisionOpened` | `commit_turn` 的 `turn.decision_request` 非空 | ❌ **不可达** | 唯一构造点在 `turn_commit.py:297-306`，而实例方法 `commit_turn` 零调用 |
| `ArtifactCommitted` | `commit_turn` 的 `turn.artifacts` 非空 | ❌ **不可达** | `turn_commit.py:271-296`；`workflow_runtime.record_artifact`（`:405`）亦零调用 |
| `StageSucceeded` | `commit_turn` 的 `next_transition.completed_node` | ❌ **不可达** | `turn_commit.py:307-317` |
| `TurnCommitted` | `commit_turn` 尾部 | ❌ **不可达** | `turn_commit.py:332-340`；其唯一读者 `EventLedger.find_turn`（`workflow_events.py:245`）也无消费者 |
| state 键 `workflow_artifacts` | `turn_commit.py:289` / `workflow_runtime.py:418` | ❌ **只写不读** | 全仓 grep：仅这两处写入，**零读取点** |

**替代路径**（为何系统仍能跑）：`planner.py:733-738` 直接对 `sync_run` 返回的 dict 赋值：

```python
# planner.py:696
            run_after = workflow_runtime.sync_run(state, context.skill_name)
# planner.py:733-738
        run_after["pending_decision"] = {...}
        run_after["status"] = "waiting_user"
```

**为何这个缺口尚未造成可观测故障**（重要，避免夸大）：机械停闸（`_apply_stage_gate`）的判据链是
`node_before ∉ completed_after`（`planner.py:712-715`）← `completed_after = _completed_nodes(...)` ← 探针 + `DecisionResolved`（`workflow_runtime.py:142`）。**这条链全程不依赖 `commit_turn`**，而 `DecisionResolved` 恰好由 `resolve_decision` 产生 ⇒ **审批节点的完成判定是活的**。

**真实危害**（这才是有价值的结论）：
1. **宪法 Rule 2 声明的「账本」只有一半是真的**。Rule 2 原文：「`workflow_runtime.py` 为**账本 + 裁判数据层**（……持久化 `WorkflowRun`，仅 runtime reducer 可改；完成度只认客观探针 stage_done……只服务审计与机械停闸判据）」。而账本中承载**产物证据**的部分（`ArtifactCommitted` / `workflow_artifacts` / `StageSucceeded` / `TurnCommitted`）**没有任何生产写入者**。
2. **审计链断在「产物」这一环**。系统能回答「哪个阶段完成了」，但**不能回答「完成时交付了什么产物」**——`workflow_artifacts` 恒空。
3. **一个反向风险**：`turn_commit.py` 那 165 行（64 个分支）是**被单测覆盖的活代码**（`tests/unit/test_workflow_v2_contract.py` 直接调模块级 `commit_turn` 断言 `c1/c2` 幂等、version 递增、`WorkflowCommitError` 抛错等）。**测试全绿，生产不跑**——这是「假信心测试」的教科书案例，直接印证主报告 E-1「门禁与测试度量的是代理指标」的判断。
4. 同族死导出（grep 零调用）：`WorkflowRuntime.recover_run`（`:522`）、`record_artifact`（`:405`）、`record_node_event`（`:350`）、`current_node_probe`（`:154`）、`planner._BG_TASKS`（`planner.py:104`，全仓仅声明与 `:115` 遍历，**无任何 `add`**）、`action_executor._describe_action`、`pause_composer.split_pause_channels`。

**正向设计建议**：不做「给 commit_turn 补调用点」的补丁，而是**让 planner 停止直写 run、把 TurnResult 作为唯一提交契约**：
```
core/turn_outcome.py
    TurnOutcome(turn_id, body, text_source, artifacts: list[ArtifactRef],
                decisions: list[DecisionRequest], produced_nodes: list[str],
                exit_reason: ExitReason)
```
`handle_message` 只**构造** `TurnOutcome`；轮末唯一调用 `WorkflowRuntime.apply(outcome) -> TurnCommit`，由它落 `DecisionOpened` / `ArtifactCommitted` / `StageSucceeded` / `TurnCommitted` 并 `save()`。如此：① 账本恢复完整；② planner 不再持有可变 run dict；③ `TestWorkflowV2Contract` 测的就是产线路径，「测试绿=产线对」重新成立。

### 新增-2【high】`platform.prompt_write` 闸机恒放行：宪法与实现漂移

> **勘误声明**：子代理称「闸门已空转 / 宪法 §2.1 仍列字数地板为强制项」。复验后**修正其归因**：这不是「实现退化」，而是**宪法文本未随一次已作出的裁决同步**。

**复验证据**：

```python
# prompt_gates.py:186-188 —— 实现侧明确声明该能力已【有意退役】
    """校验一条待写入的生成提示词。

    2026-09-10 阶段规则去代码化批（计划 B5）：**字数地板已退役**——
    平台不再以字数/结构硬拒提示词（只保留软提醒，见下 shot 软提醒），
    提示词质量与写法归 Skill 散文 + 模型自觉。

# prompt_gates.py:207-229 —— hard 列表全文无 append，恒空
    text = (prompt or "").strip()
    hard: List[str] = []
    soft: List[str] = []
    if not text or kind not in ("shot", "keyElement"):
        return True, hard, soft
    if kind == "shot":
        if (...):                      # 唯一的 soft.append
            soft.append(...)
    ok = not hard                      # ← hard 恒空 ⇒ ok 恒 True
    return ok, hard, soft
```
全仓 `grep 'hard\.append'` → **0 命中**；`hard` 的全部出现处（`prompt_gates.py:208`、`fc_tool_runner.py:269`、`fc_gates.py:388`）均为读取，无写入。

**而宪法仍把它列为强制项**：
```
ARCHITECTURE_RULES.md:82
| 平台层 `platform.*` | 生成确认闸、阶段硬边界（写文档/建结构强制暂停）、【字数地板（镜头/元素最短字数）、提示词书写闸（字数/字段）】、工具 risk 分级 | **manifest 无权关闭**；……质量闸（prompt_write、structure）严格度可经 `prompt_gate_mode`（strict/warn/off）调节……
```

**精确结论**：
- `guard_pipeline.evaluate_prompt_write`（`:90-146`）的拒收分支（`:137-145`，`mode != "strict"` 才放行，否则 `out.ok=False`）**结构上可达但前置条件永假** ⇒ `platform.prompt_write` **恒返回 `ok=True`**（`guard_pipeline.py:111/114/122/138`）。
- `fc_gates.prompt_gate`（`:350-406`）的整段升级逻辑（连续拦截计数 `ctx.gate_repeat`、`PROMPT_REPEAT_ESCALATION` 文案、`ctx.record_gen_log`）因此**全部不可达**，属宪法 §2.6「连续相同原因拦截必须升级改写指引」的**空实现**。
- **但**：这本身是 2026-09-10 的**已裁决设计**（「质量归 Skill 散文 + 模型自觉」，与 GOVERNANCE G1/G3「禁止 prose 说服、质量下沉」的方向一致），**不是 bug**。

**真正的问题是治理层的 P1 违规**：`ARCHITECTURE_RULES.md:82` 仍宣称存在「字数地板」「提示词书写闸（字数/字段）」，并把它列入「manifest 无权关闭」的强制清单。**文档与代码说了两件相反的事**，而项目自己的 `check_doc_pointers.py`（ref_integrity 闸）只查指针存在性，**不查语义一致性**。

**正向设计建议**（属主报告 E-3「P1 复述检查」的实例）：
- 立刻修 `ARCHITECTURE_RULES.md:82`：删除「字数地板」「字数/字段」表述，改为「提示词质量归 Skill 散文（2026-09-10 裁决）」，并保留 `platform.prompt_write` 条目为「结构校验（当前无硬规则，保留组合点）」。
- 更根本：给 `GATE_RULES` 的每条规则增加**活跃度字段**（`enforced: bool` + `retired_reason: str`），并加门禁：**声明为 `enforced=True` 的规则，其判定路径必须存在至少一条会产生 `ok=False` 的赋值**（AST 可判：函数体内是否存在对 `ok`/`hard` 的失败赋值）。这样「空转闸机」在 CI 即被拦下，而不是靠人读宪法发现。

### 新增-3【high】无 per-tool 超时：`_dispatch_tool` 无时限

**复验**：`grep 'asyncio.wait_for' src/` → 仅 5 处，全在 adapters/web；`fc_tool_runner._dispatch_tool`（`:311-383`）内**无任何 timeout 包装**。

**风险面**：MCP stdio 调用与外部工具一旦挂起，**阻塞整轮对话**直至用户手动停止（无回合预算，见主报告 A-2）；`_ACTIVE_LOOPS` 会让该会话后续消息全部 429。

**正向设计**：超时应是**工具声明的一部分**（policy-as-data，与 `risk`/`parallel_safe` 同族）：
```python
class BaseTool:
    timeout_s: float = 60.0        # 每工具可覆盖；None = 不限（须显式声明并登记）
```
`_dispatch_tool` 统一 `asyncio.wait_for(..., timeout=tool.timeout_s)`，超时转 `ToolResult(success=False, error_code="timeout", retryable=True)` 回喂模型（模型可换路径），并在 trace 记 `finish_reason="tool_timeout"`。对齐 DSH 的 `dsh-tool-call-timeout-policy` 包（DSH 把超时策略做成独立可插拔包）。

### 新增-4【medium】MCP 信任边界：模型可自助启用任意 MCP 工具

**复验**（子代理结论，代码位置合理，标注为「方向可信、细节未逐行复验」）：
- `mcp/client.py:78-84`：stdio transport 以配置中的任意 `command` 起子进程；`config.py:76-77` 仅校验非空。
- `catalog.py:112-136`：`mcp_tool_catalog(action="enable")` 可由模型调用，且该工具 `risk=low` ⇒ 不过 `tool_risk` 确认闸。
- `adapter.py:103`：未启用即拒执行，是执行期唯一拦截。

**判定**：属**设计取舍**（文档声明「模型可自助启用」为有意政策），但**缺少用户侧可见/可审的入口**是真实缺口——「模型自主扩大自身工具面」触碰宪法 §2.4 Context≠Consent 的精神。

**正向设计**：把「MCP 工具面扩展」提升为**显式同意事件**：
- `mcp_tool_catalog(action="enable")` 的 `risk` 由 `low` 改 `high`（它确实扩大了执行面）；
- 或保留 `low` 但要求**首次启用某 server 的工具时签发暂停卡**（复用既有 `pause_service`，与 `gen_confirm` 同构）；
- 二者取一即可，关键是「工具面变更」必须留下用户可见的同意痕迹。
