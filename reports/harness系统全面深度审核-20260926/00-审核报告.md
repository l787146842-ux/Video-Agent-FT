## 零、执行摘要

### 0.1 一句话结论

**这是一个工程纪律远超同类的项目：控制流正向、闸机分层、提示词外置、门禁机械化（含业界罕见的「门禁双向可失败性探针」）的完成度已接近工业级；但它存在一个反直觉的系统性特征——「机制被写好了、单测也绿了、生产路径却根本没接上或早已空转」，同时传统 Web 安全边界存在可被直接利用的缺陷。真正制约它的不是某个 bug，而是「治理体系给出的信心」显著高于「系统的真实状态」。**

### 0.3 三个最关键的发现

1. **【最高优先级 · 安全】`snapshots.py` 存在任意文件读取/删除（路径遍历）**。三处 `d / f"{snap_id}.json"` 对 URL 路径参数零校验；Windows 下 `Path` 的 `/` 遇绝对路径会**丢弃左侧前缀**（已本地复验）。同一仓库的 `state/repository.py:25-49` 对同类输入有白名单正则 + `resolve()` 前缀**双重**校验——**同一仓库、同一风险、两种标准**。详见 `02-安全专项.md`。

2. **【最高优先级 · 工程】大量机械机制在生产路径上「不生效」或「已空转」，而单测与门禁都显示为绿**（完整清单见 §0.4，共 6 条同族）：
   - `platform.prompt_write` 闸恒放行（`hard` 列表无任何 `append`，`grep 'hard\.append'` → 0 命中）；
   - **`web_search`/`web_fetch` 的结果进不了模型上下文**（产出 `data["output"]`，回喂层只读 `data["detail"]`）——**最具用户可见后果的一条**；
   - 工作流产物账本整层未接线（`ArtifactCommitted`/`StageSucceeded`/`TurnCommitted` 生产从不产生，state 键 `workflow_artifacts` 只写不读）；
   - 状态增量注入不生效（每轮全量重放最大 111 KB 状态）；
   - `turn_commit.py` 165 行提交逻辑被单测完整覆盖，**生产不跑**；
   - 宪法声明的六段闸机管线只有 2 段存在（`input_guard`/`tool_output_guard`/`output_guard`/`tripwire` 全仓 0 命中）；
   - 治理层同样有真空转：`docs/adr` 不存在 ⇒ `check_adr_bilateral()` 恒返回 `[]` 却报 PASS；`judge_baselines/` 恒空。
   **这些都能通过 `acceptance.py` 全绿，也都「看起来已经实现」。这是本项目最危险的特征：治理体系给出的信心显著高于系统的真实状态。**

3. **【高】上下文工程存在两个 blocker 级的结构缺陷，且四项防护在真实负载下几乎不触发**。
   - **状态注入**：每轮一份完整状态 JSON 永久留在 history，实测**占会话上下文中位 28.5%、最坏 82%**；且因 `_is_real_user_msg` 只按中文前缀判定，状态消息被当作**真实用户轮锚点**——截断时永不删除、永不被优先清理。设计的增量机制（`state_delta`）实测 **310/310 全走全量分支，delta 零命中**。
   - **多模态**：base64 图片落 append-only 事件流，`workspace/sessions/` 单文件 **50.5 MB / 183 事件**；装载层只剥离「除最后一条外的图片」——**保留的恰是最贵的那条**。
   - **防护空转**：四级保险丝（`degrade`/`truncate` 末次 **2026-09-11**、`prune` 末次 **2026-09-20**）在近 6 天生产中基本未触发——因为最大实测 prompt 129,402 tok < 预算 160,000。**截断策略在纸面上很完整，在真实负载下几乎不生效**；一旦换小窗口模型，四层会同时触发而它们之间没有协调。
   - **预算口径错误**：`tools` schema（主代理 17 个 / 11,433 chars）**不计入** max_tokens；实测 `est(total)/real = 0.666`，加 tools 后 0.968 ⇒ 系统性低估 1/3。
   - **缓存命中率是真的**：实测均值 0.645 / **中位 0.836**（915 主会话样本），证明前缀缓存设计有效；但 22% 主会话调用 `cached_tokens=0`。
   - **上下文装配散在三处竞争改写同一份 messages**（`prompt_builder` / `turn_executor` 的**逐行复制粘贴双胞胎** / `session_log`）。DSH 把这件事收敛为一个 `PromptAssembly` waterfall + 一个 `tokenMeter` 单例，本项目没有。

### 2.3 Anthropic 官方口径的对照

来自 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：

> **Compaction**：在 Claude Code 中，把消息历史交给模型总结压缩，**保留架构决策、未解决的 bug、实现细节，丢弃冗余工具输出**；压缩后继续使用「压缩上下文 + 最近访问的 5 个文件」。
> **Structured note-taking**：agent 把笔记持久化到上下文窗口之外，后续再拉回。像 Claude Code 创建 todo list，或维护 NOTES.md。
> **Sub-agent architectures**：子代理各自拥有干净上下文窗口，可能消耗数万 token 探索，**只返回 1000-2000 token 的浓缩摘要**。

对照本项目：
- ✅ 子代理架构已实现（`run_subagent` / `_launch_subagent`），且父只取子代理**最后一条非空正文**（`accumulate_visible(..., last_only=True)`，对齐 DSH 的 assistant-output 规则）——这条比 Anthropic 描述更精细。
- ⚠️ 压缩已实现且参数对齐 DSH，但**压缩指令是外置的分节**，项目自己未做过「在真实 trace 上调参」的工作（DSH 明确建议「carefully tuning your prompt on complex agent traces」）。
- ❌ **没有 structured note-taking**。DSH 的 `todo_write` 在本项目被**主动从主代理裁掉**（`CHILD_ONLY_TOOLS`），理由写得很清楚（「主代理的 todo 只是把同一份步骤誊第二遍 ⇒ 同一事实源两份（P1 违规）」）。这个理由在本项目语境内成立，但代价是**主代理失去了跨压缩的持久工作记忆**——压缩检查点成为唯一的长程记忆载体。

来自 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)：

> 三条核心原则：保持**简洁**（simplicity）、优先**透明**（transparency，显式展示规划步骤）、精心设计 **agent-computer interface（ACI）**——「我们在构建 SWE-bench agent 时，花在优化工具上的时间比优化提示词还多」。

对照本项目：ACI 投入是**明显不足的那一环**。26 个工具里 `storyboard_create_group` 的 description 有 317 字符、`todo_write` 有 278 字符，而 `storyboard_add_draft` 只有 13 字符、`storyboard_confirm_draft` 13 字符、`storyboard_delete_group` 17 字符、`storyboard_patch_draft` 21 字符——按 ACI 标准，**关键写入工具的说明严重欠费**。

#### A.2 问题与目标设计

**A-1【高】`run_agent_loop` 是 719 行的单一函数，内部嵌套 4 个闭包 + 状态机**

- 证据：`agent_loop.py:181` `async def run_agent_loop(...)` 起，至 `:899` 结束；内部定义 `emit` / `_pause_suspended_note` / `_mirror_fc_feedback` / `_stop_if_requested` / `_finalize_stop` / `_await_llm_with_stop_guard` 六个闭包，主循环 `while True` 内含 8 个 `break` / 4 个 `continue` 出口。
- 目标设计：把循环拆成 **循环驱动器（driver）+ 步骤执行器（step）+ 出口处理器（exit）** 三个具名单元：
  - `LoopDriver.run()`：只持有 `while` 与停止检查点，不含业务分支；
  - `StepOutcome` 枚举化所有出口（`Continue` / `Finish` / `Paused` / `Stopped` / `Failed`），由 `StepExecutor` 返回；
  - 出口处理收敛到 `ExitHandler.handle(outcome)`，`finally` 只做资源解绑。
  - 参照：DSH `dsh-agent-loop/src/agent.ts`（驱动器）+ `inbox.ts`（领取）+ `tool-calls.ts`（调度）三文件分离，各司其职。

**A-2【高】循环缺少「跑飞」的机械兜底，只靠输出截断 + 模型自决**

- 证据：`agent_loop.py:428` 注释「不设步数上限，靠输出 token 截断+模型自决」；宪法 Rule 2 明文「**不设步数上限**」。
- 风险：`llm_max_tokens=256000` 意味着单轮输出上限极高；模型陷入「工具→思考→工具」循环时，唯一约束是 token 账单。
- DSH 的对照：DSH **同样不设内置轮次预算**（`dsh-agent-loop` README「已知限制：没有内置轮次预算」），但 DSH 提供了**生命周期扩展点** `agent/turn-stopping` 让策略插入取消；且 DSH 有 `dsh-repeat-tool-reminder`（重复 3/5/8 次提醒）作为建议性守卫。
- 目标设计：不引入硬步数上限（会破坏「模型自决」的正确性），而是引入 **`TurnBudget` 观察者**：
  - 在 `agent_loop` 的 step 边界发出 `turn/step` 事件（已存在 `tracer.start_step`）；
  - 独立 `budget-policy` 订阅该事件，按「累计 token / 累计墙钟 / 相同工具签名重复次数」三个轴独立判定；
  - 命中阈值时**不是拦停**，而是注入一条事实消息（对齐 DSH `repeat-tool-reminder`「提醒只是建议，绝不阻止」）；
  - 阈值配置化（policy-as-data），与 `settings` 同构。
  - 这样既保住「模型自决」，又给跑飞一个可观测、可配置、可单测的阀门。

**A-3【中】机械续跑（fakestop）策略侵入循环体**

- 证据：`agent_loop.py:785-810` 在循环内直接构造 `_resume_asst` 消息、加载 `FAKESTOP_RESUME_NOTE`、`continue`。策略本应在 `round_end_policies`（`:750` 已调用 `run_round_end_policies`），但**续跑的执行动作**泄漏回了循环体。
- 目标设计：策略表返回的不是 `bool continue_turn`，而是一个 `LoopDirective`（`{kind: 'resume'|'finish'|'pause', messages: [...]}`）；循环体只做 `apply(directive)`。这样「判定」与「施加」分离，判定可单测、施加可复用（子代理/主代理同款）。

**A-4【中】纯文本轮与 FC 轮的双出口导致正文语义分裂**

- 证据：FC 分支 `agent_loop.py:606-608` 用 `accumulate_visible(..., last_only=bool(subagent_depth))`；纯文本轮走 `run_round_end_policies` 的 `false_claim_audit`。两条路径对「什么是这一轮的正文」有不同定义。
- 目标设计：定义唯一的 `TurnNarrative` 值对象（`{segments, source, mechanical: bool}`），无论 FC/纯文本/暂停轮都向它追加；所有消费方（SSE、历史、时间线、卡片）从它派生。目前项目已有「四投影同源派生」的宪法条文（Rule 2），但**代码层没有那个「源」对象**——这正是 D-21「会话投影消费方未切换」迟迟无法收口的根本原因。

#### B.2 问题与目标设计

**B-1【高】闸机链是命令式嵌套而非真管线，扩展即改函数**

- 证据：`fc_gates.py:523-545`，六道闸被写成 5 层 `if err is None:` 嵌套（其中 4 层还多缩进一级）。新增闸必须修改此函数体。
- 目标设计：`GateChain` 作为**数据驱动的有序闸表**：
  ```python
  GATE_CHAIN: List[GateSpec] = [
      GateSpec("pause_window",  pause_window_error,  short_circuit=True),
      GateSpec("tool_risk",     tool_risk_gate,      short_circuit=True),
      GateSpec("gen_confirm",   gen_confirm_gate,    short_circuit=True),
      GateSpec("structure",     structure_integrity_gate, short_circuit=True),
      GateSpec("card_media",    card_media_gate,     short_circuit=True),
      GateSpec("prompt_write",  prompt_gate,         short_circuit=True),

  ```
  执行器 `run_gate_chain` 变成 10 行循环；顺序敏感性由表序表达（可断言）；每道闸的 `rule_id`（已存在于 `GATE_RULES`）与表项一一对应，**闸机数量与注册表条目自动一致**，可用门禁机械校验。

**B-2【高】闸机规则注册表只有 3 条，与 18 处判定调用面严重不成比例**

- 证据：`gate_registry.py` `GATE_RULES` 实测 **3 条**（`platform.prompt_write` / `platform.gen_confirm` / `platform.tool_risk`）。而实际闸机判定散布在：`guard_pipeline.py`（4 个 evaluate 函数）、`fc_gates.py`（6 个 gate 函数）、`prompt_gates.py`、`planner_gate_session.py`、`round_end_policies.py`、`planner.py::_apply_stage_gate`、`fc_tool_runner.py` 调度分支等。
- 后果：宪法 §2.3 要求「策略即数据，稳定 rule_id + 层归属 + 外置文案」，但**大量判定没有 rule_id**（阶段建卡 mediaType 闸、结构完整性闸、暂停窗口闸等），因而无法进审计、无法统一文案、无法枚举。
- 目标设计：**每个判定点必须有 rule_id**。具体做法：
  1. 把 `GATE_RULES` 从「3 条平台闸」扩展为**全量规则目录**，含 `platform.*` / `skill.*` / `session.*` 三层（本项目目前只用了 platform 一层，而 `GateVerdict.layer` 字段已经预留了三层）；
  2. 在 `check_doc_pointers.py`（已有 ref_integrity 闸）里增加一条机械断言：**代码中出现的每一个 `GateVerdict(...)` 第一参数必须存在于 `GATE_RULES`**；
  3. 这样门禁从「不许硬编码字符串」升级为「每一个判定都可枚举、可审计、可文案化」。

**B-3【中】治理文档已自认的工具名分支残留**

- 证据：`docs/未清偿债务清单.md` D-10 明确列出 `fc_tool_runner.py` 仍有按工具名分支：`workflow_pause`（多处）、`storyboard_patch_draft`、`("storyboard_create_group","storyboard_add_draft")`、`("document_write","write_document")`、只读快照抑制白名单（6 个名）。

- 目标设计（补全 D-10 的要件）：在 `BaseTool` 上增加声明式元数据：
  ```python
  class ToolPolicy(NamedTuple):
      emits_snapshot: bool = False
      is_document_write: bool = False
      is_structure_create: bool = False
      suppresses_action_snapshot: bool = False
      is_pause_tool: bool = False
      parallel_safe: bool = False       # 已有

  ```

**B-4【中】工具 ACI 质量两极分化**

- 证据（实测 desc 长度）：`storyboard_create_group` 317 / `todo_write` 278 / `image_generate` 105 / `run_subagent` 98 —— 而 `storyboard_add_draft` **13** / `storyboard_confirm_draft` **13** / `storyboard_delete_group` **17** / `storyboard_patch_draft` **21** / `storyboard_patch_group` 28。
- 风险：`storyboard_add_draft` 的 schema 有 1,420 字符（含 17 个字段），但 description 只有 13 字符。模型要面对一个「17 个字段、13 个字符说明」的工具。Anthropic 的 ACI 建议是「**Put yourself in the model's shoes**……如果人需要仔细思考才能用对，模型也一样」。
- 注：`check_tool_descriptions.py` 门禁只拦「禁令句/流程纪律句/他层阶段名单」，**不检查描述是否足够**——门禁拦的是「不该写的」，没管「该写的缺失」。
- 目标设计：把 ACI 质量纳入可机械检查的维度：
  - 规则：**description 长度与 schema 字段数挂钩**（例如 `len(desc) >= 8 * max(1, n_fields)`），低于阈值即 FAIL；
  - 更进一步的规则：任一 `required` 字段在 description 中未被提及即 WARN；
  - 这比「让作者自觉」有效，且完全机械化（P2 约束下沉）。

**B-5【中】工具结果修剪是**破坏性**的，无落盘回读回路**

- 证据：`session_log.py:505-508` `PRUNE_THRESHOLD_CHARS=8192` / `PRUNE_HEAD_CHARS=4096` / `PRUNE_TAIL_CHARS=1024` / `PRUNE_MARKER="\n\n[... tool result middle pruned ...]\n\n"`；`prune_text` 直接 `head + MARKER + tail`。日志面虽保留 `pruned_from` 引用原文，但**模型侧没有取回通道**。
- DSH 的对照：DSH 有完整的三层——`output-retention`（`ItemRetainer`/`TextRetainer` 给出**精确省略计数** + `formatRetentionNotice` 标准化页脚）、`spill`（落盘返回 `locator`/`bytes`/`retrievalHint`）、`spill-policy`（`maxInlineBytes` 超过即自动转预览）。DSH 明确：「spill 失败绝不会把成功的工具调用变成错误或隐藏内容」。
- 目标设计：引入 `spill` 语义层：
  ```
  core/context_budget.py
      ├─ TextRetainer / ItemRetainer     （机制：保留头/尾 + 精确 omitted 计数）
      ├─ formatRetentionNotice(...)      （机制：标准化省略页脚）
      └─ 工具自有的恢复指引               （业务：只有工具知道怎么取回）
  storage/spill.py                       （落盘：locator = 本地路径；返回 bytes）
  ```
  修剪后的工具结果变成：`<预览 head> … <omitted N items / M bytes> … <预览 tail>` + `完整内容已保存：<path>（可用 read_uploaded_doc 或 grep 检索）`。这直接对齐 DSH，且让「模型知道自己丢了什么」——目前 `[... tool result middle pruned ...]` 连丢了多少都不知道。

#### C.2 问题与目标设计

**C-1【高】上下文装配无统一契约，三处竞争改写同一份 messages**

- 证据链：
  1. `turn_executor.call_llm`（`:249`）与 `call_llm_stream`（`:301`）**逐行复制粘贴**：`digest_projected_tool_results` → `digest_projected_tool_args` → `prune_pass` → `compact_pass` → `truncate_messages` → `_raise_if_context_overflow` → `record_live_context` → `record_prompt_fingerprint`。
  2. `planner._build_and_log_state_event`（`:1179`）独立决定状态注入。
  3. `prompt_builder.build_system_prompt` / `build_state_tail_message` 独立组装 system 与尾部。
  4. `session_log.compact_pass` 同时改写 `full_messages` **和** `mirror`（`agent_loop` 的 messages）。
- 后果：**没有任何单一位置能回答「这一步模型到底看到了什么」**。虽然有 `record_prompt_fingerprint` 兜底记录，但那是事后取证，不是设计约束。
- DSH 的对照：DSH 有明确的 **`PromptAssembly` waterfall**（`agent/request` 事件），且明文规定「**只有权威组装 waterfall 可以改变最终请求，并使其监听器负责保持协议连贯**」。
- 目标设计：建立 `ContextAssembler` 单一装配点：
  ```python
  class ContextAssembler:
      """唯一装配点：一切进入模型的内容经此产出，返回不可变 AssembledRequest。"""
      def assemble(self, *, system: str, history: list, tools: list,
                   budget: TokenBudget) -> AssembledRequest: ...
  ```
  内部按**固定顺序**执行具名阶段（digest → prune → compact → truncate → verify），每阶段产出 `StageReport`（进 trace）；`AssembledRequest` 为 frozen dataclass，`call_llm` 与 `call_llm_stream` 都只消费它——**两个双胞胎函数合并为一个**（流式/非流式只差 adapter 调用方式）。

**C-2【高】160 KB 状态 JSON 每轮注入 —— 且「增量」机制实际未生效**

- 实测：`workspace/state.sqlite3` 中 4 个项目状态，最大 **111,590 字节**（`proj-1790424553`），其余 30 KB / 24 KB / 21 KB。渲染为状态 JSON 注入 context，按 `estimate_tokens`（中文 ~1.5 字/token）粗算约 **3-7 万 token/轮**。
- **关键修正（复验结论）**：原以为 `state_delta_enabled=True` 提供了增量注入，**实测该机制不生效**——
  - `_state_digest` / `_state_hash` 是请求级 `PlannerContext` 实例字段（`planner.py:216-217`）；
  - `PlannerContext` **每请求新建**（`web/chat_service.py:497`、`:880` 两处构造点）；
  - 故 `compare_state(None, "", raw)` 恒返回 `{"_fresh": True}`（`state_delta.py:89-90`），`has_any_change` 恒 `True`（`:124-127`）；
  - ⇒ 恒走 `planner.py:1200-1206` **全量基线分支**；`build_delta_message`（`state_delta.py:135`）**生产永不可达**；
  - ⇒ `planner.py:1196-1198` 的「无变化即跳过」分支同样不可达，**不存在任何生效的状态注入节约机制**。
- 佐证：`grep -r "state_delta|_state_digest|build_delta_message" tests/` → **0 命中**（既无产线证据，也无测试覆盖）。
- 现有唯一真实缓解：`degraded_state_builder` 在超预算时降级为「只留组标题/计数」——但那是**撞墙后的保险丝**，不是预算内的节约。
- 目标设计：把「状态注入」做成 **just-in-time 上下文**（Anthropic 主张的 progressive disclosure），并让增量机制**真正跨请求生效**：
  - digest/hash 迁入**会话级持久状态**（如 `interaction.session_state`，键含 `conversation_id` + `run_id`），经 reducer 读写，而非请求级 dataclass 字段；
  - 常驻仅保留**目录级**信息（组数/草稿数/阶段/待办）；
  - 单组正文经 `read_state_group` 工具按需拉取（**工具已存在**，在 26 个工具内）；
  - 把「状态段占整轮 token 比」纳入验收观测（`prompt_builder.py:143-157` 已有 `live_metrics.record_sections` 遥测，缺阈值告警闭环）。
  - **验收判据**：连续两轮无状态变更时，第二轮状态注入必须为空（当前恒为全量）。

**C-3【中】工具 schema 每轮 7,019 token，且裁剪策略与缓存优化相互拉扯**

- 实测：26 个工具 desc+schema = 21,057 字符 ≈ 7,019 token（占 200K 窗口 3.5%，占比尚可，但在小窗口模型上是 3.5 倍差异）。

- 但仍有轮界级裁剪源（canvas 探针 / MCP 白名单 / 非 studio / `MAIN_AGENT_DENY`），而 `MAIN_AGENT_DENY` 只在 `depth==0` 且 `skill_name` 时生效——**同一会话内 Skill 激活/取消会改变 tools 段字节，击穿缓存**。
- 目标设计：把「工具可见性」定义为**会话级冻结的 profile**，而非轮级计算：
  - 会话开始时确定 `ToolProfile`（main / subagent:<stage> / adjust），整个会话内不变；
  - Skill 切换 → 明确作为「新序列」的边界（DSH 的 `startsRequestSeries` 语义），此时才允许 tools 变化；
  - 这样既保留缓存稳定，又让 `MAIN_AGENT_DENY` 的时序语义清晰可测。

**C-4【中】缺 structured note-taking（长程工作记忆）**

- 证据：`subagent.py:62-74` 详细论证了为何把 `todo_write` 从主代理裁掉（「主代理的 todo 只是把同一份步骤誊第二遍 ⇒ 同一事实源两份」）。
- 论证本身成立，但**代价未被对价**：主代理在长会话中唯一的跨压缩记忆载体是压缩检查点（由模型摘要产生，不可控）。Anthropic 明确把 structured note-taking 列为长程任务三支柱之一；DSH 的 `todo_write` 也**不回注模型**（是 UI/replay 状态），但 DSH 的 Skill **无步骤流**，所以那边 todo 是流程唯一来源——**两侧的取舍依据不同**。
- 目标设计：区分**两个不同的东西**：
  - 「Skill 步骤誊本」（本项目正确禁掉了）；
  - 「**Agent 自己的进度笔记**」——记录「我已经做了什么、当前卡在哪、下一步打算做什么」，**内容来自执行过程而非 Skill 文本**；
  - 后者的正确形态是 DSH 式的「写入即 UI 状态、不回注」，或 Anthropic 式的「NOTES.md 落盘、按需读回」。本项目 `session_log` 已是 append-only 事件流，**天然具备落盘笔记的能力**，只缺一个 `progress_note` 事件类型与一个按需读回的工具。
  - 判定标准：若一条笔记的全部内容都能从 Skill 文本推出 → 禁止（P1 违规）；若包含执行期才产生的事实（已建的组 id、已确认的参数、失败的尝试）→ 合法且必要。

#### D.2 问题与目标设计

**D-1【高】观测数据面已失控：72.77 MB trace + 全文件解析**

- 实测证据：
  ```
  data/agent_traces.jsonl      72.77 MB   (2026-09-26 20:13)
  data/agent_traces.jsonl.1     1.91 MB   (2026-09-07 03:51)
  data/agent_traces.jsonl.2     1.91 MB   (2026-09-06 21:21)
  生效配置：trace_file_max_bytes=104857600 (100 MB)
            trace_rotation_keep=10
            trace_total_max_bytes=20000000 (20 MB)
            trace_retention_enabled=False
  代码默认：trace_file_max_bytes=2_000_000 (2 MB)
  ```
- 三处不一致：
  1. `config.py:341` 代码默认 2 MB ≠ 环境生效 100 MB（有 `.env` 覆盖，但**总容量上限 20 MB < 单文件上限 100 MB**，逻辑上自相矛盾）；
  2. 轮转产物 `.1`/`.2` 停在 9 月 6-7 日 → **说明主文件自 9 月 7 日起从未触发轮转**（72.77 MB < 100 MB，所以确实不轮转——这是「配置生效后总量失控」的直接后果）；
  3. `trace_retention_enabled=False` → `compact_traces` 的三级留存**全程空转**（默认关）。
- 更严重的是读取路径：`tracer.py:754-764` `get_recent_traces(limit=50)` 遍历 `self._persist_path.read_text()` 的**每一行**并 `json.loads` 全部记录，只为取最近 50 条。在 72.77 MB 文件上，这是一个**每次调用都付出全量解析代价**的操作，而它的消费方是 `GET /api/agent/traces`（调试端点）。
- 目标设计（正向，非调参）：
  1. **审计数据与调试数据分离**：审计事件（闸机判定、控制流决策）写入**结构化存储**（SQLite 表或按日分片的 JSONL），支持索引查询；trace 全量记录降级为**采样 + 轮转**。
  2. **读取路径改为反向流式扫描**：`get_recent_traces` 从文件末尾倒读固定字节块，直到凑够 `limit` 条——O(limit) 而非 O(file)。
  3. **留存策略默认开启**：`trace_retention_enabled` 默认改 `True`；`trace_total_max_bytes` 必须 ≥ `trace_file_max_bytes × keep`（加机械断言防矛盾配置）。
  4. 加一条**配置一致性门禁**：`trace_total_max_bytes >= trace_file_max_bytes`，违反即 FAIL。这类「配置内部矛盾」正是静态门禁最擅长的领域，而项目现有的 14 条门禁**没有一条检查配置一致性**。

**D-2【中】状态写入的已知并发缺陷（D-20，项目已自认）**

- 目标设计（补全 D-20 的清偿要件）：**字段级写权分区**：
  - 每个 board 板块声明 `merge_policy: 'append' | 'lww' | 'three_way' | 'exclusive'`；
  - 写入方按板块持锁，而非整板持锁；
  - `documents` 天然 append（文档追加）、`interaction` 天然 LWW（单值状态）、`flowEvents` 天然 append（事件流）；
  - 这样版本闸从「整批放弃」升级为「**按板块分别裁决**」，消除「一处冲突、全板丢弃」。

**D-3【中】分层验证的覆盖率口径过窄**

## 五、结论

### 5.1 项目真正的优势

1. **控制流架构是正确的**。模型唯一行动主体、FC 单轨、原子轮提交、结构化暂停、协作式取消——这些不是「补丁式」的，而是正向设计出来的，与 DSH 同代共识吻合，且在某些点（会话忙闲闸、停止标志代际化、reasoning 回传口径统一）比 DSH 的公开文档描述更精细。
2. **闸机与同意的抽象层级是对的**。`GateVerdict` 结构化 + `CONSENT_CHARTER` 同意即数据 + Context≠Consent 红线 + `check_consent_copy` 一致性门禁——这是一个**可演进的安全模型**，不是一堆 if。
3. **提示词治理彻底**。42 KB 提示词全部外置，20 个文件，代码里没有超过 3 行的硬编码 prompt（并有 `check_prompt_literals.py` 门禁强制）。
4. **债务清单是真诚的**。D-10 / D-20 / D-21 条目对问题的定位、要件的设计、来源锚点都精准——这说明团队**知道**问题在哪，只是尚未排到执行。

### 5.2 项目最大的系统性风险

**架构复杂度增速 > 可验证能力增速。**

具体表现为四个失衡：

| 失衡 | 表现 |
|---|---|
| **机制 vs 验证** | 14 条静态门禁保障「结构不变形」，0 条行为评测保障「任务能完成」；**且 5 处「已实现」的机制在生产路径上不生效**（§0.4） |
| **注释 vs 代码** | 25% 的注释密度、72.77 MB trace、363 KB CHANGELOG —— 记录成本已显著高于被记录对象的更新速度 |
| **规则 vs 检查** | 宪法 §十二 有 18 项人工勾选清单，其中数项已由门禁机械强制（文档自己都注明了），却仍在清单里；`docs/adr` 扫描面恒空却报 PASS |
| **架构安全 vs Web 安全** | 闸机/同意章程/Context≠Consent 达业界水准，而同一仓库的 `snapshots.py` 对路径参数**零校验**（§0.6 S-1） |

### 5.3 最建议优先做的三件事

1. **【安全】修路径遍历 + 加路径安全门禁**（批次 0）—— 唯一「可被外部直接利用」的缺陷，修复成本半天，且仓库内已有正确范式（`repository.py`）可直接下沉为统一原语。**认证不应是路径校验的替代品。**
2. **【观测】修 trace 读取路径 + 配置一致性门禁 + 恢复本机可验收性**（批次 1.1–1.4、1.10–1.11）—— 观测面是这套治理体系的地基。实测 72.77 MB trace + 全文件解析、`GET /api/agent/traces` 是全量读；且本机 `pytest --basetemp` 权限异常使「验收 = acceptance.py 全 PASS」这条宪法条款**当前无法执行**。地基不能沉。
3. **【验证】建 `eval/` 行为评测层，把已编号事故全部转成回归场景**（批次 2.1–2.2）—— 这是唯一能打破「事故 → 加机制 → 新事故」循环的路径。项目的治理文档 **G2 关已经写明**「出方案前先查既有机制（**缺口假设须 eval 证明**）」——**项目自己规定了要有 eval，而 `judge_baselines/` 至今是空目录**。

**若只能做一件事**：做批次 0（安全）。因为它与前两条不同——前两条是「能力问题」，这一条是「**已存在的、可被利用的缺陷**」。

**若只能做两件事**：加做 **1.21（剥 prompt 分节注释）**——这是全报告**成本最低、收益最直接**的一项（一个 `re.sub`），且它污染的是**每一步回喂**（三处分节实测 273/269/163 chars，真实值应约 80/21/47），泄漏内容还是「XX 已退役」这类**系统内部机制词**，正好命中该项目自己记录过的污染事故模式。

**若只能做三件事**：加做 **1.13（修回喂通道错位）**——`web_search`/`web_fetch` 结果进不了模型上下文，是唯一一条用户能直接感知的功能性失效。
