## 一、结论（该不该加 / 加在哪 / 最小改动面）

**该加，且属「接线既有能力」而非新造能力**——与 2026-09-23 批2 补 `storyboard_delete_draft` 是**同一类缺口**
（`ops.delete_draft` 早已存在、`web` 路由早已存在，只是从未接线成模型工具）。

四层现状经实读确证（**用户背景描述全部成立，并补一处偏差**）：

| 层 | 落点 | 实测结论 |
|---|---|---|
| 领域实现 | `src/video_agent/state/storyboard_ops.py:360` `patch_group(group, patch) -> (bool, List[str])` | ✅ 存在，按 `ALLOWED_GROUP_FIELDS`（`:153-157`）白名单就地更新，`sceneRefs` 走 `dedup_scene_refs` canonical 去重（`:367`） |
| 白名单 | `storyboard_ops.py:153` `ALLOWED_GROUP_FIELDS = ("title","desc","duration","timeRange","prompt","sceneRefs","summary","elementType")` | ✅ 8 字段（含 2026-09-23 批5 新加的 `elementType`） |
| HTTP | `src/video_agent/web/routes/storyboard.py:131` `PATCH /storyboard/groups/{group_id}`（+ `:132` `/state/group/{group_id}` 别名） | ✅ 存在，但 docstring 那句 **「更新指定分组的字段（用户直接编辑，不经 Planner，<10ms）」实际在 `:134`**（`:133` 是函数签名）——用户给的「约 131」是路由装饰器行，docstring 在 `:134`。**另一处偏差**：该路由**不调 `ops.patch_group`**，而是 `svc.find_group` + `group.update(patch)`（`:139-145`）——即**绕过了白名单与 `sceneRefs` 去重**。 |
| 模型工具 | `tools/storyboard_tools.py` 的 `register_storyboard_tools()`（`:770-783`） | ❌ **无 `storyboard_patch_group`**（10 个工具：create_group / patch_draft / add_draft / delete_group / delete_draft / confirm_draft / media_to_chat / read_draft / read_state_group / view_storyboard_media） |

**结论：新增 `StoryboardPatchGroupTool`（`name = "storyboard_patch_group"`），实现体只调用 `ops.patch_group`，
不改领域层、不改闸机、不加新闸。** 最小改动面 = **4 个「必须改」文件 + 1 个 prompts 外置文件**（见 §二），
另有 3 处需用户裁决（见 §二「需要你裁决」）。

**收益（对照事故）**：9 个 shot 补引用从「23 删 + 23 建 / 261.6s / 全组 ID 换新」降为「9 次 patch / 秒级 /
ID 不变」；并消除「中途失败留下残缺故事板」的整类风险（`reports/4444-运行问题取证-20260923.md:145-147`）。

## 四、`patch_group` 够不够？——逐项判定（问题 3 的答案）

### D-1 · `sceneRefs` 三源合并：**不该在 patch 里重做**（关键取舍）

**建组侧做了什么（`storyboard_tools.py:249-269`）**：仅 `cat_key == CAT_SHOTS` 时执行
```
显式 scene_refs  ∪  ops.parse_element_tokens(desc)  →  ops.match_element_titles_report(状态)
                ∪  ops.scan_bare_name_mentions(desc, keyElements)
→ 按 ops.strip_type_prefix 归一后 canonical 去重（保序留首）
```
并回喂未匹配令牌（`:280-286`，不拒收）。

**`ops.patch_group` 做了什么（`:360-369`）**：**只做 `dedup_scene_refs`（同款 canonical 去重）**，
**不做**令牌解析、**不做**裸名扫描。

**判定 = 保持现状，不要在工具层重做三源合并。四条理由：**
1. **语义不同、不该合并**。建组是「**从零派生**引用」（desc 是素材）；patch 是「**用户/模型给了确定值**」
   （`sceneRefs` 是显式入参）。若 patch 也做三源合并，则**「把某个引用删掉」变成不可能**——
   模型显式传 `["Element_程心"]` 想删掉「走廊」，而 desc 里恰好有「走廊」二字 → **裸名扫描把它加回去**，
   形成「删不掉」的死循环（模型会反复重试，正是 4444/P1-3 那类空转形态）。
2. **`ops.patch_group` 的注释已把口径钉死**：`:366` 逐字「sceneRefs 写口**同口径** canonical 去重（与 create_group 三源合并**一致**）」
   —— 这里「同口径」指的**是去重口径**，不是合并口径。**改工具层会与领域层注释打架**（P1 单源）。
3. **有正经出路**：模型要「按 desc 重算引用」，可以 `patch {"desc": 新文, "sceneRefs": 重算结果}`
   （或先 `read_state_group` 读现状再改）。**不给隐式魔法 = 可预测**。
4. **成本**：三源合并要读 `svc.state_dict`，必须进 `async with svc.lock`（建组是这么做的），
   而参照实现 `patch_draft` 的白名单校验在锁外——语义与并发边界都会变复杂。

**若用户仍要（备选形态，最小侵入）**：只在**显式传 `sceneRefs` 且值为 `[]`/缺省**、且同批传了 `desc` 时，
才把 desc 的令牌/裸名结果合并进去；并**回喂明细**（`data["detail"]`，照抄建组 `:282-286` 的未匹配令牌告知）。
——**但我不推荐**：判据会变成「有时合并有时不合并」，比现在更难解释。

### D-2 · `sync_shot_duration`：**不该调**（且技术上也不需要）

**它是什么（`storyboard_ops.py:372-388`）**：签名 `sync_shot_duration(group, draft, patch=None) -> bool`，
语义 = **草稿**的 `duration` 与**所属分镜组**的 `duration` 对齐（仅在「patch 未带 duration 且草稿时长为空/`5s`」时补印）；
返回是否发生补印。

**判定 = 不调，两条独立理由：**
1. **签名对不上**：它作用于 **(group, draft)** 对，第三参是「**草稿** patch」。本工具没有草稿目标。
2. **语义方向相反**：`sync_shot_duration` 是「**草稿** 跟随 **分组**」（分组是权威）。
   本工具改的正是**分组的 `duration`** —— 改了时长**不会**自动传播到已存在的分镜卡。
   ⚠️ **这是一处真实但不属本工具职责的缺口**：`patch_group({"duration": "8s"})` 后，
   该组下已有分镜卡的 `duration` 仍是旧值（如 `5s`），直到该卡被一次 `patch_draft` 触碰
   （`StoryboardPatchDraftTool:323` 调 `sync_shot_duration(group, draft, params.patch)` 时才会补印）。
   **处置建议 = 本批不改，登记为待裁决项**：让它自动传播要么在 `patch_group` 里加「组时长变了就遍历 drafts 补印」
   （写面扩大、且与「用户手动设过的非默认值不覆盖」的既有判据 `:384-386` 纠缠），要么交给后续专门批次。
   **理由与本报告 C2 同构：本批是「接线」，不该夹带写面扩张。**

### D-3 · 幂等 `idempotency_key`：**必须加，且是零成本**

**机制（实测）**：
- 字段在 Input schema 里声明（`storyboard_tools.py:64/92/99/105/116/122` 六个工具都有，描述逐字一致
  `"幂等键：重复提交去重用，可留空"`）。
- 执行侧**唯一判定 = `core/idempotency_ledger.py`**：`FCToolRunner` 在闸机链**之前**取
  `args.get("idempotency_key")`（`fc_tool_runner.py:485-490`），命中即直接返回首次 `ToolResult`、跳过闸机与执行；
  执行后 `record`（`:571-572`，**成败皆记**）；账本**随轮**（`:392` `reset()`、`idempotency_ledger.py:34-36`）。
- **这是框架能力，不是工具自己的代码**：工具侧**唯一需要做的就是声明这个字段**。
- ⚠️ **不声明 = 模型传了它会被拒收**：`manager.invoke_tool` 的未知字段闸（`manager.py:211-221`）
  + `StrictToolInput` 的 `extra="forbid"`（`base.py:38`）→「入参含未知字段（已拒收，未执行）」。
  ⇒ **必须加，一行，无任何实现成本**。
- 与用户问题里的「idempotency」对照：**它就是本仓的幂等实现**，且**不是**「同键不同参也去重」的语义
  （`idempotency_ledger.py:5-7` 明写「键视为提交身份凭证，参数不参与比对」）——这正是 patch 想要的
  （重试同一逻辑提交不产生第二次写入）。
