## 2 · Q2-B 为什么**不加闸**（用户质疑「为什么要平台写死」）

用户问得对，**我采纳"不加闸"**，但理由要写清（避免被误读成"放任"）：

1. **顺序要求平台已强制**：`storyboard_tools.py` 的 `_desc_before_summary` 键序校验，
   `desc` 必须先于 `summary` —— 用户说的"先写描述再写徽标"**已是硬约束**。
2. **但键序 ≠ 内容一致**，平台不校验内容（这是对的：内容一致属创作判断）。
3. **加闸的代价实测**：t5 复算 —— 若加"summary↔desc 一致性"硬判据，
   **2222 将拒收 12/26 镜 = 46%**，误伤过大。
4. **真正的病根是 Q8**：徽标是**规划期**产物（seq=18 推理里就已定稿），
   desc 是**执行期**现编（seq=75 起批量落盘），**模型规划完不再回头核对** → 必然脱节。
   **治 Q8 才能治 Q2-B**；加闸只是把症状挡回去。

> **⇒ 结论**：Q2-B **不加闸**，改由 ⑪（进度载体）+ 现有键序校验共同处理。

## 3 · Q5 修法：**按章节与字段绑定**，不是"锁死"（用户纠正后重写）

### 3.0 ⚠️ 勘误：我上一版写「把渲染判据升格为写入判据」「锁死」——**框错了**（用户纠正）

用户原话（准确）：
> 「音色建到关键元素里面不稳定，**锁死应该不对吧**。skill 都明确交代了**在关键元素的设计环节**，
> 而且**字段也是关键元素的字段**，是不是应该**和对应的章节和字段绑定**才对呀。」

**船长复算后确认用户对**：问题不是"要不要加一把锁"，而是
**平台从未把 Skill 的「章节」与看板的「类目/字段」绑定起来**——
Skill 说了（归属），字段也备了（承载），**唯独中间那条绑定链缺失**。

### 3.1 证据：Skill 已经把归属说清楚了

`<storyboard_key_elements>` 原文（逐字）：
> 「角色的声音特征（音色/语气/情绪基调）**单独登记为 key_element_audio**，
> **与角色元素绑定**，用于视频生成时的音频条件。」

**⇒ Skill 的语义非常明确：`key_element_audio` 属于「关键元素」章节的产出。**

而 `<storyboard_audio>` 章节全文（船长实取）只管三件事：
> 「**BGM**：全剧至少规划一条背景音乐轨……**旁白**：如有画外音/旁白，以 narration 类型登记……
> 视频生成阶段视频本身不内嵌 BGM」

**⇒ 同章节分工清晰：音色卡归 key_elements，BGM/旁白归 audio_layer。** 两者本不该混。

### 3.2 证据：字段也确实备好了（用户说得对）

| 层 | 现状 | 证据 |
|---|---|---|
| **渲染层** | **已备**：keyElement 组内 audio 卡渲染为半尺寸小卡 | `DraftCard.tsx:92` `isVoiceCard = type==='keyElement' && mediaType==='audio'`；CSS `.draft-card--voice{58×32}` |

### 3.3 证据：缺的正是"章节 ↔ 类目"这条绑定

船长全仓检索（`verify_5_61b.py`）：

- 平台现有映射表**三张，没有一张是「章节 → 类目」**：
  | 表 | 左值 | 右值 |
  |---|---|---|
  | `registry.CAPABILITY_TOOL_STAGES` | 能力 | **section 名**（`storyboard_ke`…） |
  | `skill_docs.SECTION_TAG_STAGES` | 章节 tag | **stage 名**（`planning`…） |
  | `storyboard_ops.category_for_group_type` | **工具入参** `group_type` | 类目（`keyElements`…） |
- 交叉检索「章节名 + 类目名」同现的文件：`storyboard_ke`+`keyElements` → **无**；
  `prompt_draft`+`keyElements` → **无**；`storyboard_shot`+`shots` → **无**；
  `storyboard_audio`+`audioItems` → **无**。
- 关键：`category_for_group_type` 只看**模型传的 `group_type`**：
  ```
  category_for_group_type('keyElement') = 'keyElements'
  category_for_group_type('audio')     = 'audioItems'     ← 模型传 audio 就落音频层
  category_for_group_type('')          = 'keyElements'    ← 缺省归 keyElements
  ```

**⇒ 所以模型把音色建成 `group_type='audio'` 时，平台"没有任何机制"知道
「这张 audio 卡其实是 `key_element_audio`、该归 keyElements」** ——
**平台把"这张卡属于哪个章节"这个信息，完全丢给模型自己声明（`group_type` 入参）。**
这才是"不稳定"的机制根源。

### 3.4 修法（按用户思路：章节与字段绑定）

**核心：让"当前委派阶段"成为归属的判据来源，而不是靠模型自报 `group_type`。**

1. **建立「章节 → 类目」绑定**（新增一张表，唯一事实源）：
   `storyboard_ke / storyboard_key_elements` → `keyElements`；
   `storyboard_shot` → `shots`；`storyboard_audio` → `audioItems`。
2. **写入时据此判定归属**：子代理在 `storyboard_design` 阶段建
   `key_element_audio`（mediaType=audio）时，**归属由章节决定 = `keyElements`**，
   不依赖模型传 `group_type`；
3. **字段级判据**：`key_element_audio` 的合法承载 = **keyElement 组内的 audio 卡**
   （与渲染层 `isVoiceCard` 同口径——**渲染层与写入层从此共用一条判据**）；
4. **`audioItems` 类目只承载 `<storyboard_audio>` 章节的产物**（BGM / narration）；
5. **存量修复必须走"补建"**：全库 audio 卡=0 ⇒ **无卡可移**，"移动卡"逻辑会做错。
