## 6.4 「@[角色代号] 为什么没解析上去」

**实测确证：本平台解析不了带方括号的 `@[角色代号]`**（`.tmp_probe/test_at_parse.py`）。

`core/prompt_refs.py:22` 的正则：
```python
_MENTION_RE = re.compile(r"<<<\s*image_([^<>]+?)\s*>>>|[@＠]([^\s@＠]+)")
```
`[^\s@＠]+` 是**贪婪**的，会把方括号一起吃进去：

| 输入 | 捕获到的名字 | 结果 |
|---|---|---|
| `@程心` | `程心` | 正确 |
| `@[程心]` | **`[程心]`** | ❌ 名字含方括号 |
| `@[角色代号]` | **`[角色代号]`** | ❌ |

端到端（`resolve_prompt_mentions`）：**三种写法挂上的参考素材都是 0 张**——因为
`build_storyboard_media_map()` 的键是**分组标题（带 `Element_` 前缀）或草稿 label**，
而提示词里写的是**裸名**，`media_map.get("程心")` → `None` → 走"未命中：去掉记号保留文字"。

**⇒ 6.4 的真实结论（比"没解析"更严重）**：
1. 方括号**会**被吃进名字（形态不兼容）；
2. 即使不带方括号，**裸名也对不上 map 的键**（前缀问题，与 Q4 同源！）；
3. `replicate exactly` 这句话**原样保留在解析后的提示词里**——但它是**英文散文**，
   平台**没有任何代码消费它**（无对应参数、无引用、无校验）。
   它是否有用，取决于生成渠道是否把提示词当自然语言读——**本平台没有把它变成结构化约束**。
4. 3333 实测：`media_map` 的键数 = **0**（因为当时 17 张卡都还没出图，`imgUrl` 全空）。
   ⇒ **提示词先于出图写入**，导致 `@` 引用**在写入当时必然解析不到任何素材**（时序缺陷）。

> 待 flova 审计报告补充"还有哪些字段没用上"。

### 6.1-b ⭐ 船长深挖：用户「才到 planner 第 4 步」的判断切中要害

用户原话：「明明才到 planner 的**第 4 步，第四步就是只写关键元素**。是因为主代理没有给子代理
交代任务导致的么？」

**船长核查后：任务书不是主因；真正的结构性缺陷是「阶段粒度 vs planner 步骤粒度错配」。**

#### 证据一：planner 的第 4/5/6 步是**三种不同的提示词**，分属三个不同生产动作

`data/skills/AI-短剧一站式生成/SKILL.md` 的 `<planner>` 流程（逐字）：

| planner 步 | 原文（节选） | 产出 | 时机 |
|---|---|---|---|
| **第 3 步** | 「设计 Storyboard：登记所有 key_element（角色、场景、关键道具），将剧本拆解为有序 shot 列表，规划 audio_layer」 | keyElement + shot + audio | **设计期** |
| **第 4 步** | 「生成所有 key_element 设定图（角色三视图、场景四视图）：提示词先经 storyboard_patch_draft 写入草稿」 | **KE 设定图提示词** | 生成期 |
| **第 5 步** | 「生成每批次运镜轨迹示意图（分镜表格图）…提示词先经 storyboard_patch_draft 写入草稿」 | **分镜表格图提示词** | 生成期 |
| **第 6 步** | 「逐 shot 生成视频…视频提示词先经 storyboard_patch_draft 写入草稿，再调用 generate_video」 | **视频提示词** | 生成期 |

#### 证据二：平台把第 4/5/6 步的提示词**全部塞进同一个阶段**

`src/video_agent/skill_runtime/registry.py:46`：
```python
"write_media_prompt": ("prompt_draft",),
```
而 Skill 的 `<write_media_prompt>` 章节**同时包含三套模板**（船长实取小标题，逐字）：
```
**内切镜时长估算（视频提示词撰写前）**
**角色三视图提示词（TextToImage…）**          ← planner 第 4 步
**场景四视图提示词（TextToImage…）**          ← planner 第 4 步
**分镜表格图（运镜轨迹示意图）提示词（ImageToImage…）** ← planner 第 5 步
**单 shot 视频提示词**                        ← planner 第 6 步
**固定尾部规则：**
```

**⇒ 所以用户说的现象有了准确解释**：
模型被委派一个 `write_media_prompt` 阶段（展示名「提示词编写」），
注入的章节里**三套模板同时在手**，而平台的目标行又说「完成本阶段**全部**产出」
——**它没有任何线索知道"现在该做第 4 步、不该做第 5/6 步"**。
于是它把三套一次性全写了（3333 实测：每个 shot 组内**同时**有
「运镜轨迹示意图提示词」(image) 与「视频提示词」(video)，17 个 KE 组另有设定图卡）。

**⇒ 你的判断是对的，只是原因不在"主代理没交代"，而在"阶段的粒度 ≠ planner 步骤的粒度"**：
- planner 把提示词拆成 3 步（4/5/6），**且每步之间有暂停点**
  （Skill `<planner>` 的「关键暂停点」：设定图确认后才进分镜表格图，全部表格图后才进视频）；
- 平台把 3 步合成**1 个阶段** `write_media_prompt`；
- 结果：**跨阶段（4→5→6）的边界在平台侧不存在**，模型自然一次做完。

**⇒ 这也修正了此前"非越权非漏放"的定性**：
t2 说 47 张卡建在 `write_media_prompt` 阶段属"合法"——**就"平台没限制"而言合法**，
但**就 planner 的步骤纪律而言，第 5/6 步的产物在第 4 步被一并产出，正是用户指的"跨越阶段"**。
两者不矛盾：**平台无约束（合法）＋ Skill 有步骤纪律（越步）**。

> 「阶段粒度 / 目标行粒度」的平台侧（另见 6.1 与第 8 条同源）。

后台调研中期结论曾称「失败信息……没有被特殊豁免」。**船长复核推翻该表述**：

注释**逐字**为「**never corrective feedback**」，判据 = `decision.kind !== 'accept'`。

`packages/core/tools/src/index.ts:596-602` 的类型定义：
```ts

  | { kind: 'accept'; content?: ContentBlock[]; value?: never; additionalContexts?: UserMessage[] }
```

**⇒ dsh 有两条路径，必须分开对待：**

| 类别 | dsh 的 decision.kind | 是否截断/spill |
|---|---|---|
| **工具执行失败**（跑了但失败、或输出超大） | `accept` + `isError: true` | **会** spill → 头尾预览 + 定位符（`spill-policy.spec.ts:211-241` 实证） |

**⇒ 对本项目 Q9 的最终口径（经 t5 调研员反向纠正后修订，见 9.3）**：
