# Q7 · 类目 × 媒体能力矩阵

## Q7 结论

1. **【确证】平台不存在「类目 × 能力」矩阵。** 唯一按类目分支的逻辑是
   `stamp_draft_spec_preference`（补印默认分辨率/时长/供应商），
   它是**补默认值**，不拒收、不放行、不决定按钮可见性。
2. **【确证】唯一按 mediaType 拒收的闸机是「阶段闸」不是「类目闸」**：
   `STAGE_CARD_MEDIA` 键 = `storyboard_design`（**阶段名**），
   消费端 `card_media_gate` 读 `ctx.stage_card_media`，
   **从不读 `group_type`**，且只覆盖 `storyboard_add_draft` /
   `storyboard_create_group`（内联 draft），**不覆盖 `storyboard_patch_draft`**。
3. **【确证】「出图/出视频/出音频」的可见性 = 前端三处分支的合成结果**，不是查表：
   `ParamControls`（按 `selectedType` + `genType` 分发参数栏 → 也就决定了出现哪个按钮）
   + `GenTypeTabs`（**只在 keyElement 渲染**，可把 genType 切成 image/video/audio 任一）
   + `ImageParams`/`VideoParams`/`AudioParams`（按钮）。
4. **【确证】后端生成入口对「类目」零校验**：`generate_image` / `generate_video` /
   `batch-image` 三个路由只校验「prompt 非空」「provider 非空」「draft 能找到」，
   **不校验 draft 所属类目**。
5. **【确证】类目约束缺失已经在两个项目上造成实际混装**（见 §Q7-证据-5）。
6. **【判断｜推测成分已标注】「目标矩阵」若要用代码落地，正确归属层 = `docs/GOVERNANCE.md` 修复决策树里的**
   **「工具面/写闸」而不是「Skill 散文」**——因为 Skill 已把语义说清（
   `<storyboard_key_elements>`：「角色三视图/场景四视图是 image_generate 的产物」；
   `<storyboard_shots>`：「每个 shot = 一次生成任务」），
   问题在于**平台没有任何一处把它变成可判定的约束**。详见 §Q7-可判定性。

### 放大因素 1 · 建组键序校验（`desc` 必须先于 `summary`）——**一次撞墙让整批 3 个调用全废**

**校验实现**：`src/video_agent/tools/storyboard_tools.py:48-67`
```python
@model_validator(mode="before")
@classmethod
def _desc_before_summary(cls, data):
    if isinstance(data, dict) and data.get("group_type") == "shot":
        keys = list(data.keys())
        if ("desc" in keys and "summary" in keys
                and keys.index("desc") > keys.index("summary")):
            raise ValueError(
                "shot 建组入参键序错误：desc 必须先于 summary（先写完整镜头"
                "设计 desc，再据其提炼 summary 徽标）；请调整字段顺序后整单重填。")
    return data
```
**它校验的是 JSON 键的物理顺序**（`mode="before"` 收 `json.loads` 保序 dict）。

**实测后果**（2222 子代理 `conv-1790091784-91e4b9b5.jsonl`；段号取 `_work/stats_v2.txt` 的 v2 口径）：

| 事件 | seq | 段/步 | 时刻 |
|---|---|---|---|
| 1 次发出 3 个 `storyboard_create_group` | 68 | 段 8 / step 9 | 23:44:48 |
| 3 条 `tool/result` 均为 `[validation] … shot 建组入参键序错误：desc 必须先于 summary…` | 69 / 70 / 71 | — | — |
| 下次响应仍发 3 个 `create_group`（**已改正键序**）→ 3 条均成功 | 75 | 段 9 / step 10 | 23:45:20 |
| 3 条成功 `tool/result` | 76 / 77 / 78 | — | — |

**代价**：
- 段 8 的 `reasoning` 为 3871 字、`text` 130 字——**这一步的推理与正文全白费**；
- 23:44:48 → 23:45:20，**多耗 32 秒**（该步 LLM 生成耗时本身只占 23.0s）；

**注意**：合并阶段（`storyboard_design`）合并了三阶段后，
这个"只对 shot 生效"的键序校验**覆盖面未同步评估**——
`_desc_before_summary` 只判 `group_type == "shot"`，合并本身不影响它，
但合并**改变了模型的组织方式**（一次委派内既建 KE 组又建 shot 组），
键序约束的"存在感"随之上升。此条标注为**观察，非结论**。
