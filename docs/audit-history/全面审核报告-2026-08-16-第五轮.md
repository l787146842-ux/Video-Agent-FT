## 三、指令治理审计（是否混乱）

**结论：主干不混乱，是目前见过的最系统的指令治理实现；但存在 3 处层间张力 + 2 处
宣称漂移，应按台账机制登记或归位。**

### 3.1 实测健康面

- system.md 774B / system_fc.md 1750B，远低于 7KB 预算；共有段 {{include}} 共源，零复述；

- 回喂话术（层 8）均为「客观回报+单句下一步」，未见夹带规则（抽验 agent_loop
  L597-625、planner fc 回喂）；
- 状态即数据（P3）：状态 JSON 注入语只有一句客观引导，未见说教嵌入。

### 3.2 张力与漂移（需登记/归位）

- **#4 skill_discipline.md 归属层漂移**：第 8 条规定了具体产出形态（中文叙事式多节拍、
  摄像机→主体→空间→音频顺序）——按 13.3 这是层 3（Skill 产出规范）/层 4（铁律）
  的内容，现内联在平台层注入块（legacy 兜底路径）。若某 Skill 要求英文分栏式提示词，
  平台纪律会与其打架（裁决链虽然用户>Skill 可救，但靠裁决不如归位）。
  且文件标题「最高优先级」与 13.3 裁决顺序（用户最新指令 > 铁律+规格 > Skill > 平台）
  表述冲突。**处置：登记 T18（可接受张力）或把产出形态条款迁入铁律模板**。
- **#5 important_rules.md 双表述张力**：【提示词质量铁律】硬编码「电影级 6 大核心规则」
  作为平台默认，同文件末条又说「拆解质量规范由所选 Skill 规定」。有兜底语（未选 Skill
  时才套用），但「铁律」命名+平台层承载 Skill 级质量条款，与 13.3「项目级生产契约归
  层 4」不符。**处置：登记或下沉铁律模板**。
- **#1 i18n 宣称漂移（实测新发现）**：四轮 R3/#5 宣称 SSE status 全量 i18n 化，但——
  ① `planner.handle_message_stream` L706-719 的 step_started/actions_applied/
  executing_actions 三处队列级 status 仍是硬编码中文、无 key；
  ② 前端 `chat.ts` L146-148 消息 meta「耗时 Xs / N 轮 / 更新 N 项」硬编码中文未走 t()。
  属台账宣称与代码不符的第三例（同类：N7/R2 漂移先例），**应按 N7 勘误机制登记并清偿**。

## 四、Skill 体系审计（不同形式能否充分发挥）

**支持形态（实测齐备）**：
1. flova 原生 `<tag>` 章节式（SECTION_TAG_STAGES 14 标签映射，含一对多：
   storyboard_designer 三拆同时映射 ke/shot/audio）；
2. 本地 Markdown 标题式（_HEADING_STAGE_HINTS 关键字兜底 + 上文阶段沿用）;
3. 有/无 skill_manifest（未声明=最小闸，S1 语义）；
4. 有/无可解析章节（auto：执行器形态 vs 全文兜底直注；executors/legacy 强制档）；
5. pause_rules 显式声明块（优先于自然语言「何时暂停」检测）；
6. spec_wizard / script_required **客观文本特征探测 + manifest 逃生门**（不预设、不强迫）；
7. 外来工具名映射对照表（flova 原生工具名 → 本系统动作，防幻觉调用）。

**评价**：对「外来成熟平台 Skill」的适配是当前体系最精巧的部分——章节按执行器分注、
流程基线 <planner> 注入、外来工具名映射、阶段聚焦再强调，四层逼近原生平台的分工具
注入效果。**不同形态的 Skill 均能发挥作用**，结论成立。

**发现的问题**：

- **#6 标题式解析的静默沿用**：split_skill_sections 中标题未命中关键字时「沿用上一个
  已识别阶段」——新形态 Skill 的章节可能被**静默归错阶段**且无任何告警。
  处置：解析时对「沿用超过 N 节仍未命中」记 warning + 入降级遥测；扩 split 结果黄金
  快照（R6 模式复用：16 存量 Skill 的章节解析结果钉死）。
- **#7 resolve_entry 模糊匹配**：双向包含匹配（长度≥2 即试）在同名前缀 Skill
  （如「古风甜宠短剧」vs「古风短剧」）间可能错配。处置：精确/归一化未命中时，包含
  匹配要求唯一命中，多命中记 warning 并返回 None（宁可要求用户选准）。
- **T16/T17 维持原判**：渠道参数写死与暂停点自然语言解析上限均已登记，本轮不重复立案。

## 六、Agent 交互体验审计（重中之重）

> 范围：对话内除用户气泡外的一切 agent 侧呈现与交互。

### 6.1 现有设计清单（逐项验证，均为已实现）

| 元素 | 实现 | 评价 |
|---|---|---|
| 阶段完成卡 StageCard | 默认展开、概述+执行清单、与正文判重防双显、历史可回看、已回应/已过期徽标（R3/#10） | 优 |
| 确认交互 ConfirmActions | group 分页向导（逐页选/末页合并发送）/单选卡片/厂商模型下拉/自定义输入框/选项 value 机械消费 | 优 |
| 过程时间线 AgentTimeline | 深度思考视窗（定高滚动+智能追底）+ 操作条目（运行走秒/刷新重建/子挂父后） | 优 |
| 流式体验 | 边写边填卡片逐张亮、status 状态栏（i18n key）、reasoning 实时流、停止键 | 优 |
| 闸机可见性 | chips 来源标注 + 本次放行（知情文案）+ 纯文本 warnings 分离 | 优 |
| 文档卡片 | doc_written 即显（四段链）+ done 去重 + 点击开文档面板 | 优 |
| 排队引导 | 推理中发消息入队、可「引导」移队首、轮间注入不打断、原位转圈 | 先进 |
| 记忆命中 | memoryHits 折叠可视化 | 良（透明度好） |
| 生图结果 | imageCard 缩略图/lightbox/拖拽/下载 | 优 |
| 错误处理 | 鉴权类错误附「检查 API 配置」跳转；空响应用户腔兜底 | 良 |

**总评**：交互设计的**深度**超过绝大多数同类产品——暂停卡生命周期、仲裁可观测、
放行知情同意、思考与工具耗时分离计算，都是踩过真实事故才做得出的细节。

### 6.2 发现的问题（按体验影响排序）

- **#2 消息流碎片化（最值得改）**：finishStream 把文本气泡、每个 docCard、imageCard
  分别 push 为**独立 ChatMessage**（chat.ts L176-188）。一轮「写 3 个文档+出 4 张图」
  会在对话流里产生 5 条并排 agent 条目，无轮次容器、无头像分组，历史回看时一轮的
  产出被打散，与 StageCard 的「一轮一卡」心智模型不一致。**改进见 M1**。
- **#3 缺重试/续跑的一键入口**：空响应兜底引导用户「直接说重试」（文字约定），
  但没有可点击的重试按钮；多步被 max_steps 截断后也无「继续」按钮。agent 侧交互
  过度依赖用户手打。改进：done payload 携带 `retryable`/`continuable` 标记时渲染
  对应按钮，点击发送固定 value（沿用选项 value 机械消费模式，P2 确定性三问全中=收归系统）。
- **#1 i18n 残留**（见 3.2，体验面：切英文后 meta 与部分 status 仍中文）。
- **#12 确认选择的回看缺失**：用户点了向导选项后，选项卡随消息保留但**看不出当时
  选了哪项**（选择以普通用户消息发出，需向上翻找）。轻量改进：ConfirmActions 在
  其后出现用户消息后（confirmState=answered）把已选 label 高亮/标注。
- **#13 放行作用域语义**：overrideOnce 发送 `gateOverrides:['all']`，后端消费逻辑里
  `any(startswith("platform."))→"all" else "element_image"`（planner L311-314）——
  「非 all 即 element_image」的隐含映射只有两处代码懂，前端/按钮/审计三端没有共享的
  作用域枚举。改进：作用域枚举单一常量 + trace 记录实际消费 scope。

### 6.3 判定：是否合理

**合理，且高于行业基线**。现存问题（#2/#3/#12）属「从可用到好用」的打磨，不涉及
范式错误；唯一结构性建议是引入**轮次容器**（M1），它同时解决碎片化与确认回看。

## 十、改进方案（按宪法四关自检：G1 未动 Skill、G2 均复用既有机制、G3 无 prose、G4 同类覆盖）

### M1 轮次容器（#2/#12，交互体验核心改进）

- **设计**：引入 `turnId`（后端 done payload 已有 trace 可携带）；前端 messages 渲染
  层按「相邻 agent 条目同 turnId」聚合为一个轮次容器：StageCard/时间线/气泡/docCard/
  imageCard 全部收进同一容器，容器头显示模型名+耗时 meta（替代逐条 meta）。
- **确认回看**（#12 顺带）：容器 answered 态时 ConfirmActions 已选项加对勾标注
  （纯前端：其后存在用户消息且内容等于某选项 value/label 即判定）。
- **兼容**：旧消息无 turnId 时每条自成一容器（行为不变）；持久化结构不动
  （渲染层聚合，不改存储）。
- 验收：vitest 快照（聚合前后 DOM 结构）+ 用户目测。

### M2 确定性按钮化（#3/#11/#13）

- done payload 增 `suggested_actions`（数组：`{kind:"retry"|"continue"|"waive", value, label}`）：
  空响应→retry、max_steps 截断→continue、剧本闸→上传引导。前端渲染为按钮，
  点击走 sendUserMessage(value)——**沿用选项 value 机械消费既有模式**（G2）。
- 放行 scope 枚举常量化（#13）：`GateOverrideScope = "all"|"element_image"|"flow"`
  单一常量源，前端按钮/后端消费/trace 记录三端引用（G4 同类全覆盖）。
- user_insists_override：按钮化上线后降级为纯兜底，同时补 intent 语料快照钉死现状。

### M3 兼容壳清偿一轮（#10/B-1）

- 以 `兼容层移除计划.md` 为台账，把 11 个壳文件按「测试 patch 目标已迁移」分批删除；
