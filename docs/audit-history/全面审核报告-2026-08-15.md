### 2.2 判定结论

**整体合理，噪音主要来自三处**：
1. toast 与对话内卡片的双重展示（#16/#17）——信息已经在对话里了，toast 只剩打断；
2. 阶段卡形同虚设——只有标题和徽标，规范承诺的「展开看本轮概述+执行清单」未实现，用户想知道「刚才到底做了什么」只能去翻折叠的时间线（而时间线默认是折叠的！两条信息通道都默认关闭，完成后的第一眼只有一句标题）；
3. 两条「轮间注入/即显」通道断线导致体验退化回 3333/7777 事故前状态（见 §3.1），但前端 UI 已按「通道活着」设计（handler 都在），形成「界面期待功能、后端不发货」的隐性割裂。

### 2.3 重点问题清单

1. **【P0】doc_written（3333 修复）四段链全断**：`sse_events.py:24` 定义常量；`chat.ts:240-245` 前端 handler 完好；但后端零发射点（fc_tool_runner 的 `doc_written` 只是同名局部布尔变量），`planner.py:703` 白名单、`chat_service.py:821` 白名单均不含该事件。→ 长批拆解时文档卡又回到「轮末一把出现」。
2. **【P0】guidance_injected（7777 三轮修复）无调用方**：`agent_loop.py:264-285` 的轮间注入依赖 `pending_injector` 参数，`planner.py:566-578` 调用 run_agent_loop 时**未传** → 事件永不发出。当前排队消息的唯一出路是任务结束后前端自动重发（`ChatInput.tsx:148-156`），「轮间注入」机制整体是死代码。前端 `use-sse.ts:244-247` 的 handler 和 `sse_events.py:41` 常量同样沦为死资产。
3. **【P1】阶段完成卡与规范/台账双重不符**：814G1 台账声称「阶段卡恢复可展开」，规范要求默认展开+正文+执行清单；实现只有 header。`msg().confirm` 字符串（系统精心生成的暂停文案）在前端从不渲染，仅作布尔标志位——用户看到的是「关键元素拆解 · 阶段完成（更新 N 项）」一句话，真正的暂停说明只在模型正文气泡里。
4. **【P1】闸机警告的挂载逻辑是字符串匹配**：`ChatFeed.tsx:65` `w.includes('拦截')||w.includes('闸')` 与 `ChatMessageItem.tsx:54-55` 双重复制同一脆断判定。文案措辞一改（或未来 i18n）按钮即静默消失；「闸」字还误伤任何含「闸」的正常文案。宪法 §2.3 要求 verdict 结构化，但 warnings 至今是纯字符串数组，未携带 rule_id/layer。
5. **【P1】双轨闸机用户可见性不对称**：文本轨拦截原因进 `result.warnings`（agent_loop.py:406）→ 有警告行+「本次放行」按钮；FC 轨拦截原因只进 `fc_tool_runner.gate_warnings`（fc_tool_runner.py:548），该列表**无任何生产消费方**（grep 证实仅 skill_runtime/executors.py:719 与测试引用）→ FC 轨用户只看到时间线红叉「被流程门禁拦截」，看不到原因、也拿不到「本次放行」按钮。违反 §2.0「同一请求判定逐字节一致」与 §2.4「拦截必须用户侧可见」。
6. **【P2】toast 风暴**：`use-sse.ts:291-298` 一轮 done 最多连弹 3 类 toast（素材插入/操作数/逐条警告），而三类信息都已在该轮消息内可见。
7. **【P2】「引导」中断无确认**：`QueuedMessagesBar.tsx:33-37` 点击「引导」立即 `stopAgentStream()` 杀掉进行中任务再自动发消息。用户认知是「排队+优先」，实际是「中断+重来」，误触代价高；建议改「完成后优先」或加确认。
8. **【P2】内部术语泄漏**：`fc_tool_runner.py:931-934`「剧本分析未完成（script_analyze 执行失败）」、`:965-968`「{_failed} 执行失败」把英文工具名直接给用户；时间线摘要 fallback 用工具名当文案（`AgentTimeline.tsx:38` `a.summary || a.name`）。

### 3.2 FC 轨警告外发断线（P0）

`fc_tool_runner.execute()` 返回 8 元组 `(applied, confirmation, image_urls, chat_inserts, action_log, confirmation_options, tool_results, docs_written)`——**没有 warnings**。`self.gate_warnings` 收集了流程门禁原因（:621）、生成确认闸（:531）、KEY_ELEMENT_FIRST（:690）、规格豁免（:859），但返回后无人读取。修复：返回值补 warnings，`planner._handle_fc_response` 并入 `loop_result.warnings`，与文本轨对齐。

### 3.3 model_fallback 载荷错误（P0）

`chat_service.py:849-853`：失败候选 `(cand_provider, cand_model)` 时下发 `{"provider": cand_provider, "model": next_model}`。fallback 链是「同模型跨厂商」（`_fallback_candidates` 注释明示），即 model 全程不变，真正变化的是 **下一候选的 provider**（`candidates[idx+1][0]`）。前端 `applyFallbackModel`（agent-prefs.ts:103-113）按该载荷匹配 → 找到的还是失败供应商 → 选择器要么不动要么跳回失败方。应下发 `candidates[idx+1][0]`。

### 12.3 臃肿七型（证据 → 定位 → 判定）

**A. 事故补丁沉积层（最大来源）**
36 起事故 → 每起落「闸机条款 + 回喂模板 + 卡型 + 台账行 + 测试文件」。典型化石：
- 22 个事故编号测试文件（`test_1111_fixes.py`…`test_output_budget_fixes.py`）约 3,800 行，与按功能命名的测试（test_planner/test_memory…）重复覆盖同一代码；
- `agent_loop.py:598-701` 一处文件内连续 8 个「卡注入点」（规格暂停/审阅/向导/收集/结构自检/结构审阅/阶段兜底/剧本强制），每个都带自己的 `if not confirmation` 守护——逻辑正确但读起来已无人能一眼推演出「这一轮最终会弹哪张卡」；
- `fc_tool_runner.py` 批末 5 段「防虚报覆盖」文案（:884-972）层层互斥（`if … and not …`），新增第 6 种失败模式时没有人知道该插在哪层。
**判定**：不是删功能，是「卡注入决策树」需要收敛为一张显式状态机（见 12.6）。

**B. 双轨复制冗余（结构性冗余之最）**
FC 轨与文本轨为维持「判定逐字节一致」，把闸机逻辑复制三份：`fc_tool_runner.py` 903 行 + `action_executor.py` 943 行 + `agent_loop.py` 730 行 + `guard_pipeline.py` 155 行 + `skill_runtime/guard.py` 81 行 ≈ **2,812 行**。宪法 §2.0 要求的「同一管线实例」只覆盖了 `prompt_write_verdict` 一层，流程门禁（FlowGate）、规格闸、结构闸、防虚报在双轨是**两套手写镜像**——本次审核已抓到镜像漂移（FC 轨 gate_warnings 不外发，§3.2）。文本轨的存续理由只剩「gemini-cli 等无 FC 通道」，但该通道的闸机完全可以复用 FC 轨的校验函数而非复制。
**判定**：长期必须收敛（文本轨=无工具通道，执行器与闸机共用 FC 实现），中期至少把 `agent_loop.py` 中 8 个卡注入点抽成单一路径函数供双轨调用。

### 12.4 根因分析（为什么 AI 协作必然走向臃肿，本项目为何更重）

1. **补丁驱动 + 现场就近补条款**：宪法 13.4 明令禁止，但 36 起事故的实际落点证明「闸机加一条 + 卡加一张 + 测试加一个」比「重构归属层」短期成本低——AI 助手按短期最优行动，臃肿是累计最优的副产品；
2. **双轨是复制放大器**：每新增一条闸机，FC/文本两处镜像 + 循环骨架一处判定 = 3 处，且「逐字节一致」只能靠人工目测与测试比对（本次已漂移）；
3. **删除恐惧 > 删除纪律**：DEPRECATED re-export、models_legacy、launcher 重定向、mock 双轨、归档入库——宪法只有「DEPRECATED 保留别名导入不立即删」的宽限条款，没有「删除计划与到期执行」的强制条款；
4. **前端重写未断舍离**：旧 studio 的 i18n/theme/设置页以 iframe 形式整体存活，重写完成后没执行资产退役；
5. **数据无生命周期**：写入路径都有、清理路径全缺（traces/tasks/history/logs）；
6. **治理文档的宣称与代码脱钩**：台账靠人肉登记，回退事故后无人反向校验（814 系列本身就是证据）。

## 14. 对话栏全流程端到端深审（追加重点）

> 方法：以「右侧对话栏」为唯一视窗，从「加载/不加载 Skill」起步，逐阶段追踪：冷启动 → 输入 → 发送 → 后端全链路 → 卡片/正文/思考 → 结束/历史回看，专项审计**响应速度、流程规范、合理性、系统返回消息的真实性**。

### 14.1 阶段 A：冷启动与 Skill 加载（或不加载）

1. 启动 → 项目状态快照装载（含 skills 列表）→ `SkillPicker` 显示全部 `data/skills/*.md`。
2. **【P1】「不加载 Skill」路径 UI 不可达**：`SkillPicker` 无「不使用技能」选项（SkillPicker.tsx:100-189 只有卡片/眼睛/加号/导入）；且 `agentSkillId()`（agent-prefs.ts:75-81）在 localStorage 无值或失效时**自动回落第一个技能**。因此「无技能」状态只有两种入口：从未有技能文件、或删除技能后未再选择——正常安装下**每一条消息都携带 skill_name**（agent-actions.ts:154），planner 恒以「有选中 Skill」模式运行（gate_enabled=True、注入执行器块/全文、装配 flow_gates）。后端完全支持空技能（最小闸），但前端不提供入口 → 设计缺口，应加「不使用技能」卡（或选中态可取消）。
3. **【P2】「当前技能」三本账**：localStorage 选中（agent-prefs）↔ usedSkills 登记（仅消息带 chip 时，chat_service.py:571-573）↔ skill_name 请求携带（恒带）。用户点技能卡后删掉 chip 再发送 → Skill 生效但 docs 面板不显示、`skill in selected_skills` 类闸（agent_loop.py:440 规格向导拒收）不生效。同一事实三个来源 + 四级 fallback（chat_service.py:129-158），建议收敛为单一「当前技能」客观状态（随项目持久化）。
4. Skill 文档懒加载（docs.ts:37-49）✅，冷启动无额外开销。

### 14.2 阶段 B：输入与发送

- 富文本混排、媒体 chip、@画布提及、粘贴/拖拽上传、附件条、排队区——机制已审（§2.1），发送前无阻塞点；
- 发送请求体含 `images/videos`（全部故事板媒体 URL 清单，agent-actions.ts:144-145）——素材多时请求体大，首包发送延迟线性增长（P3，可改为服务端按需取）。

### 14.3 阶段 C：首响应时间（TTFT）审计——首 token 前的串行开销清单

| 序 | 开销 | 位置 | 量级 | 判定 |
|---|---|---|---|---|
| 1 | 暂停消费/规格定稿（锁内状态操作） | chat_service.py:242-254 | 毫秒级 | ✅ |
| 2 | 多模态内容构建（Pillow 缩放至 1024 长边） | multimodal_builder | 9 图约 1-3s；**CPU 同步调用位于 async 路径，疑似阻塞事件循环**（未核实 run_in_executor） | ⚠️ 速度疑点 |
| 3 | fallback 候选链（合并画布 providers，HTTP） | chat_service.py:685-713 | 首次较慢，有缓存 | ✅ |
| 4 | **会话 compaction 摘要 LLM 往返** | chat_service.py:274-325 | 第 13 轮起，每次发送多一次独立 LLM 调用（便宜模型，2-10s）才进主循环 | ⚠️ 建议预热后台（任务创建时 fire-and-forget，命中缓存） |
| 5 | 每轮全量重拼 system prompt | prompt_builder.py:40-159 | 协议 14.3KB + 铁律全文 + Skill 全文（≤30K 字符）+ 状态 JSON + 记忆块——**首 token 前置成本与 prompt 体量成正比**（臃肿直接转化为速度损失） | ⚠️ 与 §12 瘦身联动 |
| 6 | 记忆检索（chromadb 同步查询） | prompt_builder.py:98-112 | context_builder 是同步函数，chroma 查询/关键词打分阻塞事件循环 | ⚠️ 建议 run_in_executor |
| 7 | 首轮 LLM 流式 → 首个 delta | planner llm_call | 模型原生延迟 | ✅ |

**速度结论**：短对话（<12 轮）TTFT 正常；长对话受 compaction 摘要 + 大 prompt 双重拖累；多图场景受 Pillow 阻塞影响。三项改进（compaction 预热、Pillow/记忆检索移出事件循环、prompt 瘦身）可把中位数 TTFT 显著降下来，且全部是低成本改动。

### 14.4 阶段 D：多步循环内的速度与规范

- 纯规划计时正确（planner.py:512 在 `_handle_fc_response` 之前取数，工具耗时不进「规划」行）✅；
- FC 工具逐个 await 串行，每个有实测耗时条目 ✅；
- 写提示词执行器的速度治理是亮点：快模型级联先试（C5）、零进展批内纠正并升级回主模型（executors.py:1895-1934）、撞线预算翻倍封顶 32768、进度播报带总批数与「可中断可续写」语义 ✅；
- 空输出自动重试 ≤2 次（状态可见「输出异常，重试中」）✅；结构首建强制自检轮 = 用额外一轮 LLM 换质量（台账已裁决）✅；MAX_STEPS=6 与 system.md「最多 6 轮」一致 ✅；
- 阶段边界动作流式预执行被延迟（_STREAM_GATE_DEFER_ACTIONS）——正确性优先，无速度问题 ✅。

### 14.5 阶段 E：系统返回消息的真实性审计（卡片/正文/思考，逐项判真伪）

**真实（可信）**：
- 时间线规划行耗时 = 纯模型规划；工具行耗时 = 实测（FC 轨）；失败态补发防「永远转圈」✅；
- 「耗时 Xs · N 轮 · 更新 M 项」= t0→done 真实墙钟（含 compaction/fallback，口径诚实）✅；
- mock 模式明确标注「回复由本地规则生成，未调用真实 LLM」（mock_chat.py:59）✅；
- 「已完成：X」状态仅从**成功**动作的 action_log 生成（agent_loop.py:515-517）✅；
- 文本轨拦截原因进 warnings 行 + 时间线红叉 ✅（FC 轨例外，§3.2）。

**失真/半失真（本次新发现）**：
1. **【P2】「深度思考 Xs」角标高估**：`thinkingMs` = 首条 reasoning 增量 → done 时刻（chat.ts:136-137），reasoning 与工具执行交错，done 前夹着全部工具耗时——「深度思考 12.3s」实际混入执行时长；且多轮只算最后一轮；
2. **【P2】文本轨批量操作耗时均摊**：`per_ms = _batch_ms / len(new_logs)`（agent_loop.py:519-525）——5 个操作 3s 各显 0.6s，是平均值不是实测（FC 轨为实测）——时间线的「白谎」；
3. **【P3】三种空回复占位并存**：后端「已更新。」/「（无回复）」（planner.py:750）vs 前端「（空回复）」（chat.ts:142）——前后端文案不统一，刷新后还会跳变；
4. **【P3】docCard 与正文双显**：正文「本轮已写入文档：《X》」（planner.py:626-631）+ docCard 卡片同屏出现——同一事实两遍，轻量噪音；
5. **【P3】思考全文持久化入库**：trace.steps[].reasoning 全量落盘（每轮万字级思考 × 每消息），与「不进上下文」承诺一致但存储成本高——建议入库前截断（如尾部 2K 字符）；
6. 前奏条目 elapsed=0（「加载 Skill」0.0s）——诚实但观感怪，建议隐藏耗时而非显 0。

### 14.6 阶段 F：结束与历史回看

- done → 快照同步 → 记忆后台记录（不阻塞）✅；排队自动出队（失败丢消息，§7 已报）✅/⚠️；
- 历史回看：时间线从 trace 重建同构 ✅；warnings 常驻 ✅；**历史暂停文案不可读**（吸收 Qoder 问题 12）❌；空回复占位跳变（14.5-3）⚠️。

### 14.7 阶段 G：流程规范符合性端到端

- 阶段边界暂停 = 模型自发 + 层 9 兜底卡 + flow_gates 硬拦 + 结构自检轮四层保障 ✅；
- 生成确认闸 / 元素图就绪闸（只警告不拦人）/ @引用自动补写 / 时长同步 / 剧本原料闸三路语义 ✅；
- **【P1】Skill 自定义「何时暂停」节无运行时消费点**：`skill_requires_stage_pause()`（guard.py:74-94）的消费方仅 skill_docs.py 保存时 lint 提示——运行时没有任何机制按 Skill 声明的暂停点强制暂停，skill_discipline.md:2「Skill 里每一个确认/暂停点都必须真正停下」实际只靠模型自觉 + 平台兜底卡近似。13.7 耦合点表亦未登记此断线。修法二选一：FlowGateSet 消费 pause 声明（客观状态触发暂停卡），或修订 discipline 文案承认兜底语义（不得两版并存）。
