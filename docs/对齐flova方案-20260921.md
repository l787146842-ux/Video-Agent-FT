## 三、批 1：修主代理角色定义（核心）

### 问题

`protocol.md:1` 说主代理是"编剧+分镜师+视觉总监"，与 09-19「纯编排」裁决矛盾，且这句位置最靠前、权重最重。

### 改法

把第 1 行改成**与 09-19 裁决一致**的调度层定位，并对齐 flova 的措辞：

```
你正在驱动影视 Agent 工作台，角色是制片调度：理解用户需求、维护项目文档、
判断流程顺序与暂停点、把各专业阶段委派给对应执行环节。
各阶段的专业创作（剧本分析、故事板设计、提示词撰写等）由对应执行环节完成，
你不亲做。动作通道唯一 = 系统提供的 Tool 调用（Function Calling）。
```

**要点**：
- 「制片调度」取代「编剧+分镜师+视觉总监」——**单一自我定位，与新裁决一致**
- 明确"你不亲做"——这句是 09-19 裁决应有的**自我认知侧**表述，此前只在 `skill_runtime.md` 里有（且那条讲的是"章节注入"，不是"你是谁"）
- **不新增 prose 禁令**：只是把已经裁决过的分工写到角色定义里（P1：规则搬家到正确的位置，不是新增规则）

### 同时修第二处：`protocol.md:13` 的规格边界 —— **【本版大改】**

现在是**一句压缩的纯否定**：

```
- 规格文档只承载全局决策参数（画幅/时长/风格/声音与语言），渠道/分辨率/分镜上限由全局设置注入，实体细节归元素与故事板工件
```

**它有三个问题**（本节为 2026-09-21 用户裁决后重写）：

| # | 问题 | 后果 |
|---|---|---|
| a | 告诉模型"**不该**写什么"，**没告诉它"可以不写"** | 收了实体细节后陷入"不能不写、又没地方写" → 塞进规格（2222 实测） |
| b | **缺"分析得到的事实可写入"** 这一档 | 分析出来的**全局**事实（叙事驱动、核心视觉母题）没有合法去处 |
| c | **缺"未确认的不得写成规格"** | 模型可以把"待用户补充"的项写成既定规格 |

**【修改说明 · 用户 #6】**：原方案第 ③ 条写的是「**已确认的全局约束**（如输出语言/画幅/风格）」——**这是错的，用户指出"不要框的太死"**。

核实：制作设定与剧本**子代理本来就自读得到**，2222 实测两个子代理**都真的读了**：

| 子代理 | 实际读取动作 |
|---|---|
| `storyboard_key_elements` | `read_uploaded_doc`（剧本）+ `read_project_doc`（制片规格.md） |
| `storyboard_shots` | `read_uploaded_doc` + `read_project_doc` ×2（剧本 + 制片规格 + 执行铁律） |

**所以父代理复述全局约束 = 纯冗余 + 双份事实源。** 改成只写「**尚未落入制作设定的新决定**」——即那些子代理**读不到**的东西（比如用户刚在对话里拍板、但还没写进规格的参数）。这才是任务书真正**必须**承载的部分。

**【增加说明 · 用户 #7】**：末句「写制作设定时按写入原则分档」是**用户明确要求加上的**（"这个很重要，本项目也要加上，**任务书上要加上**"）。它把 §三 的四档原则**同时**下发到委派语境——因为写规格的动作既可能发生在主代理（`document_write`），也可能发生在委派决策时（"哪些该进规格、哪些该留给子代理"）。**两处同源引用，不复制正文**（P1：`protocol.md` 是唯一正文家，此处只写分档要点）。

**要点**：
- 保持"只写一句目标"的**精神**不变，但给出**可照抄的形态**（模型更容易执行"写成这样"，而不是"别写那三样"）
- 补上**"为什么"**：`你复述只会和章节打架`——这是 2222 实证的真话（两个子代理对"分镜草稿"理解相反，就是因为父代理各自写了一套）

## 五、批 3：`run_subagent.stage` 暴露枚举（D1 对齐，用户已同意）

### 问题

`document_tools.py:893-898`，`stage` 的 description **刻意不列名单**，只说"由系统枚举"。2222 实测：模型**必猜错一次**（先填中文"剧本分析"被拒 → 改 `script_analyze`），花 3.5s + 一次失败往返，**且每个新会话都会重犯**。

### 改法

**既有先例**：`storyboard_tools.py:33-36` 的 `_DRAFT_FIELDS_HINT` 就是**动态拼接白名单**：

```python
_DRAFT_FIELDS_HINT = (
    f"合法字段（白名单外字段整单拒收）：{', '.join(ops.ALLOWED_NEW_DRAFT_FIELDS)}。"
    ...
)
```

且该文件注释明写设计意图：

> 对齐 dsh schema 精确性：**模型看得见字段就不用猜**

**照此办理**（`document_tools.py`）：

```python
def _stage_hint() -> str:
    from src.video_agent.core import subagent as _sa
    return "、".join(f"{k}（{_sa.STAGE_LABELS.get(k, k)}）"
                     for k in sorted(_sa.PIPELINE_STAGE_KINDS))

# stage 字段 description 改为动态拼接：
description=f"本次委派推进的生产阶段名。可选值：{_stage_hint()}；留空 = 通用委派。"
            "填写后系统自动把所选 Skill 对应阶段的章节全文注入子代理（章节即产出规范），"
            "任务书里不用复述规范。"
```

**要点**：
- **仍然是单一事实源**（运行时从 `PIPELINE_STAGE_KINDS` 读），只是把它暴露出来——不产生第二份事实源（不违反 P1）
- 顺带把中文标签也给出（`STAGE_LABELS` 已有），模型不用英中转换
- **保留 fail-loud 校验**（`fc_tool_runner.py:296-302` 不动）——description 是引导，校验是兜底，两层都在

### 为什么这是 DSH D1 的正解

DSH `tools.restrict()` 在报错时列出**全部已知工具**（`index.ts:1097`）：

```ts
throw new Error(`tools.restrict() names unknown global tool(s) ...; known global tools: ...`)
```

DSH 的理念是：**能让模型不猜的地方，就不要让它猜**。我们现在有报错时列白名单，**但正常路径上不列**——等于"考完试才给答案"。

### 回归测试

- 锁 `RunSubagentInput` 的 `stage` description **包含 `PIPELINE_STAGE_KINDS` 的每一个键**（防止有人改枚举忘了改 description）
- 锁 description 含中文标签（可选值可读）

## 九、【本节新增】子代理工具面没有按阶段收口 —— 回答用户 #8

### 用户的问题

> 工具都是子代理该用的工具，为什么子代理会有纠结算不算越权呢？**是什么限制了子代理**，让它有这样的想法？

**用户问得对，而且查出了一处硬缺陷。** 子代理的纠结**不是它多疑**，是平台**散文宣称了阶段级授权，代码却没真的实施**。

### 事实：设计意图 vs 代码实际

`core/subagent.py:91-107` 的注释写得很明确：

> 阶段执行器必备工具集（正向设计单一事实源）：**每个可委派阶段的子代理在其上下文内调用的生产工具**。

按设计，`storyboard_key_elements` 阶段的子代理**应该只有** `storyboard_create_group` + `storyboard_delete_group`。

**实际算出来的工具面**（我实跑验证）：

```
阶段: storyboard_key_elements
子级 deny 集 : ['generate_video', 'image_generate', 'read_skill', 'run_subagent', 'workflow_pause']
设计宣称的工具集: ['storyboard_create_group', 'storyboard_delete_group']

子代理实际可见工具数: 18 / 23
其中【非本阶段】的落账工具全都还在:
   document_write              ← 可见
   script_analysis_report      ← 可见
   storyboard_add_draft        ← 可见 ★
   storyboard_confirm_draft    ← 可见
   storyboard_patch_draft      ← 可见 ★
   storyboard_media_to_chat    ← 可见
```

**`storyboard_add_draft` 和 `storyboard_patch_draft`（正是写提示词用的两个工具）在这个阶段**根本没有被收走**。

### 代码层面为什么

`planner.py:355-357`，子级工具面的真实算法是：

```python
deny = getattr(context, "subagent_deny", None)
if deny:
    excluded |= set(deny)
```

而 `subagent_deny` 来自 `child_deny_set(stage)`（`subagent.py:171-176`）：

```python
def child_deny_set(stage: str = "") -> FrozenSet[str]:
    return SUBAGENT_TOOL_DENY | (
        STAGE_TOOL_DENY_EXTRA if resolve_stage(stage) else frozenset())
```

**它只返回两个集合的并集：**
- `SUBAGENT_TOOL_DENY` = `{run_subagent, image_generate, generate_video, workflow_pause}`（**与阶段无关的固定四条**）
- `STAGE_TOOL_DENY_EXTRA` = `{read_skill}`（带 stage 时加这一条）

**`_STAGE_TOOLS` 表压根没进这个函数。** 我全仓搜了 `stage_tools()` 的调用点：

```
src/.../subagent.py:152          ← 只有定义
tests/unit/test_production_prune.py  ← 只有测试
```

**`stage_tools()` 在生产运行时零消费者。** `_STAGE_TOOLS` 表只被用于：
- ✅ 装载期 fail-loud 校验（枚举漂移检查）
- ✅ `MAIN_AGENT_DENY` 子集校验
- ❌ **从不用于限制子代理的工具面**

**结论**：`_STAGE_TOOLS` 是一张**声明性表格**——它表达了"每个阶段该用什么工具"的**设计意图**，但**没有接进执行路径**。子代理的收口只做了"四条固定 + read_skill"。

### 这如何解释 2222 的实测行为

回看关键元素子代理的推理原文（`conv-1789905193-bcf55a17.jsonl` seq 7-8）：

> 「不过音频元素要等 audio 阶段（storyboard_audio 章节），本次委派目标是 key_element。**所以本次只做 keyElement 分组，audio 不在本次委派范围**」
> 「我的落账工具 = 该阶段生产工具，即 storyboard 系列工具。**委派目标没有包含 audio 登记。保守起见**…」
> 「为了**不越权**（audio 不在本次委派核心范围）…这是合理的折衷，且不跨阶段。」

**它为什么纠结？因为平台给了它两套互相矛盾的信息：**

| 信息源 | 说什么 | 性质 |
|---|---|---|
| **工具面**（可执行权限） | 你有 18 个工具，`add_draft`/`patch_draft`/`document_write` **都在** | **实际能力** |
| **章节 + 任务书散文** | 你是 key_elements 阶段，只登记元素 | **散文约束** |

**模型看到的是**：散文说"你只管 key_elements"，但**它手上真真切切握着 `storyboard_add_draft`**。于是它必须**自己判断**：这工具是给我用的吗？用它算不算越权？

**这就是"纠结"的来源**——不是模型多疑，是**散文与工具面不一致**，模型被迫在信息冲突里自行裁决。

**而它最终选了"写提示词"**（17/17 张卡全带 prompt），因为：
1. 任务书**明确要求**了（"并为每个元素编写设定提示词草稿"）
2. 工具**真的在手**（`create_group` 内联 `draft` + `add_draft` 可见）

**两票赞成，只有散文一票反对**——它当然越界了。

### 对照 flova

flova 在这点上是**结构性**的。用户引用的原话（L763）：

> **不可以**。子代理不能在执行过程中自行自由读取文档区的其他文档或 skill.md 的其他章节；**它只能使用运行时注入的对应 Skill 分区、共享项目状态，以及被明确传递给该任务的资源**。

而 L708-710 说得更直接：

> **工具职责隔离**：主代理没有"直接生成媒体""直接写入故事板结构""直接编辑成片时间线"的**执行权限**。它只能调用相应的专业环节。

**flova 的隔离是"工具面真的没有"**，不是"散文说你不该用"。所以 flova 的子代理**不需要纠结**——它手上就那些工具。

**这正是 DSH D1（`tools.restrict`）的设计理念**，也是我上一版说"同意 D1"的实质——但**我没想到 D1 在我们这里根本没接上**。
