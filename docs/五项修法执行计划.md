## 一、背景与已定裁决（**不要再议**，遇反对意见引用本节）

### 1.1 事故（为什么做）

4444 项目（`workspace/state.sqlite3` → `proj-1788701482-49d721f6`，Skill「AI-短剧一站式生成」，模型 glm-5.3-flash）：用户确认制片参数后，模型在「默认（原生）」思考档发起调用，**思考内容耗尽 `llm_max_tokens=8192` 输出预算** → 返回空/畸形（finish_reason=length、正文空、无工具调用）→ `agent_loop` 判空分支**同输入全价重试 2 次**（每次约 3.5 分钟）→ 共约 10 分钟零产出，用户手动停止（原子轮废弃，状态零损失）。

根因链：① 输出预算 8192 对思考型模型太小；② 判空分支不看 `finish_reason`，"预算截断"与"真空响应"同罪同罚；③ 重试 = 同输入原样重跑，必现同结局。

### 1.2 业界调研结论（2026-09-06/07 联网 + 源码实证，已定）

- **dsh**（`deepseek-ai/deepseek-harness`，DeepSeek 官方开源，MIT）：默认单次输出预算 `DEFAULT_MAX_TOKENS = 256_000`（`packages/llm/llm-deepseek/src/adapter.ts:142`）；撞帽（finish=max-tokens）→ 本轮以该原因收尾，**绝不原样重试**，UI 有专属 turn-max-tokens 提示节点；**循环里没有"空响应重试"分支**（正文空+无工具调用 = 正常收轮 `completed`）；工具调度 = 按工具声明执行模式（parallel / exclusive 屏障）+ 有界并行池（`DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10`）+ 模型序提交 + 中止时为未启动调用补合成错误结果；压缩摘要撞帽 fail-closed（"incomplete checkpoint"）。
- **Claude Code**（泄漏源码架构分析）：主循环五条静默恢复路径（collapse drain → reactive compact → 输出预算 8k→64k 升档重试 → "please continue" 续写 → schema 重注），穷尽才报错；**每条恢复路径配熔断**（20 个 `MAX_*` 常量；教训：1,279 会话连续 50+ 次压缩失败、日耗 25 万次 API 后才加）；StreamingToolExecutor（参数块流内生成完即执行）；**无"每步一调用"的强制或提示条款**。
- **Codex**（OpenAI 官方《Unrolling the Codex agent loop》）：循环同构；Responses API 跨步保留 reasoning items（思考不从头重来）；提示词缓存纪律；上下文自动压缩（`/responses/compact`）。
- **总结论**：没有任何一家强制"一步一调用"；没有任何一家让用户调输出预算；两家路线（大帽子 vs 小帽子+恢复路径）殊途同归。

## 三、四批修法（每批独立 commit，按序执行）

### 批 1（止血）：输出预算 256k 级 + 内部压缩撞帽 fail-closed

1. `config.py` 的 `llm_max_tokens`（原默认 8192）→ 默认 **256_000**（对齐 dsh；max_tokens 是上限不是目标，不产生额外费用）。注意 `config.py:410` 附近 `SETTINGS_GROUPS["llm"]` 键表带该键，核对分组文案。
2. `token_budget.py` 的硬编码表 `_MODEL_OUTPUT_LIMITS`（deepseek/qwen=8192、gemini/gpt-4.1=32768、gpt-4o=16384、claude=8192）外置到 **`data/model_output_limits.json`**（沿用 `_load_context_windows` 同款懒加载 + 损坏降级空表骨架，子串先到先得），补录 glm/zhipu 等已知保证值；`output_limit_for_model` 改读 JSON，**签名不变**；`tests/unit/test_output_budget_fixes.py` 表值断言同步。
3. `openai_compat.py` 新增「400 拒收大 max_tokens → 钳制重试一次」分支：复用 `_strip_unsupported_on_400` 的 400 捕获 → 改 payload → 重试一次 → 按模型记忆 骨架，但 `max_tokens` 是**改值**不是剥离——钳到 `output_limit_for_model(model)`。三处下发点统一：`chat()`（None 回落处）、`chat_stream()`（同）、`_try_chat_fallback`（内联 payload 处）。
4. fail-closed：`round_compact.py` 摘要调用与 `history_compact.py` 摘要调用各加 `resp.finish_reason == "length"` 判定 → 走**既有**异常回落分支（半截摘要不入 `_COMPACT_CACHE`、不落 `interaction.session_summary`）。
5. 测试：表值与回落、400 钳制重试与按模型记忆、两处压缩撞帽回落。

### 批 2：撞帽/判空收轮语义（policy-as-data，删盲重试）

1. `recovery_policy.py`（模块头宪法：新失败类型=表中加行，**禁循环内私设恢复分支**）：新增 `FAILURE_OUTPUT_TRUNCATED`（finish_reason=length）；`FAILURE_BAD_OUTPUT`（空响应+stop）保留但 action 从 `nudge_retry` 改为新的 `ACTION_END_WITH_NOTICE`（收轮 + 用户可见提示，不重试）。`classify_step_failure` 按 finish_reason 分流到两个键。
2. `agent_loop.py` 判空分支（符号锚点 `_bad_pol` = `recovery_for(FAILURE_BAD_OUTPUT)`，现状 `while not content.strip() and fc_applied == 0 and bad_retries < max_retries`）改为：先看 `finish_reason`——`length` → 截断收轮（warning「本轮生成在输出预算处被截断」+ 既有 suggested action `retry` 芯片）；`stop` 且空 → 空响应收轮（独立 warning 文案）。**删除同输入重试循环**；`_bad_output_nudge` 函数与 `prompts/planner/feedback.md` 的 `BAD_OUTPUT_NUDGE` 分节随之退役（全库搜引用后删）。非空但 `length` 截断的既有轮末警告（「被 max_tokens 截断」）保留。
3. 用户可见通道：复用 done payload 的 `warnings`（前端 GateWarnings 已渲染）+ `suggested_actions`（retry 芯片已有）——**零新增 SSE 事件、零前端改动、不触发 gen_api_types/sse_protocol 门禁**。
4. 测试：截断不重试、空响应不重试、非空截断保留警告、表驱动分派断言；`test_sse_protocol_chain.py` 等门禁回归。

### 批 3：单步并行池（按工具声明，deny-by-default）

1. `tools/base.py`：`BaseTool` 加 `parallel_safe: bool = False` 类属性（默认 False=独占串行；先例 = `risk`/`costly`/`provider_kind` 声明轴）；`tools/manager.py` 注册期校验非 bool 拒收（照 `costly` 的校验段）。
2. `fc_tool_runner.py` 的 `execute` 主 for 循环（现严格串行 `_dispatch_tool`）改为**分桶执行**：连续 `parallel_safe=True` 的调用进一组（asyncio 有界并发，池上限常量 4），独占调用自成屏障；**结果与 SSE 事件按模型顺序提交**。保持既有语义不变：批首 checkpoint（`batch_has_risky_tool`）、问即停（`workflow_pause` 永远独占）、幂等账本、取消路径（已启动的跑完，未启动的记合成「已取消」结果——对齐 dsh `appendSkippedToolCall`）、独占失败回滚-中止纪律；并行组内失败**不级联**（组员均为只读）。
3. 本批只给三个只读工具标记 `parallel_safe = True`：`read_skill`、`read_draft`、`list_skills`（模型惯于并行连发，7777/4444 实证）。其余工具一律默认串行。
4. 测试：新增分桶/模型序提交/取消补结果单测；既有 runner 相关 20+ 测试文件回归（清单见 §五）。

### 批 4：GLM 思考回传调研 + 能力探测（第 5 项）

1. 联网调研智谱 GLM OpenAI 兼容层：工具循环是否要求/接受 `reasoning_content` 回传（DeepSeek 官方是"必须回传"，GLM 侧待证实）。
2. 若支持：实现 default-off 的 `llm_reasoning_passthrough` 设置——请求侧对 assistant 历史消息附加 reasoning 字段（400 剥离机制天然兜底拒收）+ 会话消息结构加字段（`state/manager.py` `add_chat_message`）+ `truncate_history` 透传（`chat_opening.py`）——三层组合改动。
3. 若不支持/查无实据：**不动架构**，结论与前置条件登记 CHANGELOG 调研留痕（第 5 项的交付物 = 结论）。
