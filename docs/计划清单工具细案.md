## 一、机制定位（抄 dsh 的通用形态，五件套）

| dsh 做法（证据） | 本项目对应设计 |
|---|---|
| 整表替换：每次传完整清单覆盖旧表，无局部更新（index.ts:45-66） | 同：入参只有一个 `todos` 数组 |
| 三态 pending/in_progress/completed（L26） | 同，字面值一致 |
| 「至多一个 in_progress」代码硬校验，违反→isError 回喂自纠（L91-111） | 同：ToolResult(success=False, error_code="validation") |
| 时机软引导写在 description，不设「不建清单不许干活」硬闸 | 同（G3 边界：校验是代码、时机是 description，两分） |
| 不进每步注入，模型靠回看自己历史里的工具调用参数看进度；投影只喂 UI（Agent Note L23-25） | 同：这是缓存设计的核心决定，见 §四/§五 |

class PlanItem(StrictToolInput):

## 三、校验与错误回喂（代码硬校验）

`aexecute` 入口顺序校验，任一失败整次拒收、旧清单保留：

1. 空清单 / 超 24 项 → 拒；
2. content 去空白后为空 / 项间重复 → 拒；
3. in_progress 计数 > 1 → 拒（dsh L107-109 同款）；
4. status 非三态 → 代码校验拒收（实现注：不用 Literal 天然拒——Pydantic 报错话术
   不受控、超 3 句口径；统一走 validate_plan_items 的 bad_status 码，话术纯事实）。

错误话术 ≤3 句、纯事实+补救（v4-1 口径），例：

> 清单校验失败：发现 2 个 in_progress（至多 1 个）。本次未写入，保留上次清单；合并为单一进行中项后整表重提。

成功返回极小：`data={"items": n, "open": m}`（不回显清单——清单字节只存在于模型自己的 tool_call 参数里，见 §五）。

## 四、状态落盘与注入面

- **落盘**：`svc.state_dict["plan"] = {"items": [...], "updated_turn": turn_seq}`，直写 + save，不走 update()（analysis 先例 analysis_tools.py:79-82，不污染 undo 账本）。
- **轮首状态事件**：`_build_snapshot_dict`（[context_builder.py](file:///e:/07%20天问/自己做agent/src/video_agent/state/context_builder.py) L99-131）加 `plan` 键（空清单不注入，省字节）。状态事件本来就是每轮新追加的尾部消息（planner.py:836-863 签发，source=state），**不触碰历史前缀**；体积上限 24×40 字 ≈ 1K 字符，不进 STAGE_STATE_FOCUS 裁剪表（非分组类别）。
- **门禁同步**：`_BOARD_PROJECTION_KEYS`（context_builder.py:457-460）加 `plan`，过 check_category_keys 闸。
- **不发事件卡**：event_cards.py:36-78 无映射即 []（document_write 非规格名 / workflow_pause 不发卡先例）——计划更新高频，发卡会撑大 flowEvents 进上下文。前端计划面板直接读状态投影，不走卡。
- **stage_probes 不读 plan**：阶段判定仍 = 产品存在性（stage_probes.py:80-120），plan 只是进度账，两套判据不交叉（防「清单全勾 ≠ 产物落地」的假完成，机制二对账时另核）。
- **机制二接口预留**（本批不实现）：RoundEndContext 未来加一等字段 `plan_open`（agent_loop 构造点从 state 读），供兜底闸口判「还有未完成项不许静默停」；AST requires 自检强制显式登记（round_end_policies.py:329-380），不留 getattr 后门。

## 五、缓存影响评估（专章）

**净增量清单（全部核过，共四处，仅一处进 tools 段）：**

| 注入面 | 影响 | 定性 |
|---|---|---|
| tools 段（现 7497 tokens） | schema +description 约 +100-150 tokens，**tools_fp 一次性翻转** | 部署后各项目首调冷一次（设计内代价，同历次加工具） |
| 轮首状态事件 | plan 非空时 +≤1K 字符/轮，且是**每轮新追加的尾部** | 不击穿历史前缀 |
| 步间 | **零注入**（dsh 形态：不进 system 重渲染、不进步尾消息、不发卡进 flowEvents） | 前缀 append-extension 性质保持 |
| 工具结果回喂 | 成功仅 `{items, open}` 数十字节；失败回喂 ≤3 句 | 远小于 E2 修剪门槛 8192 码点，不触发修剪 |

**一个要明说的代价**：E2 修剪器只裁 `role=tool` 消息（session_log.py:505-575），**不裁 assistant 的 tool_calls 参数**——模型每整表重写一次，旧清单参数就永久留在历史里（dsh 同款：last-write-wins 靠参数回放）。上限核算：每次 ≈1K 字符 × 一轮重写 3-4 次 ≈ 每轮 +3-4K 字符历史增量，由「阈值压缩 80% 触发」兜底（已上线机制，非新账）。24 项/40 字上限就是把这笔账钉死在可预算范围内。

**批 0（观测前置，先于工具本体合入）**：给 `record_cache_usage` 调用点（turn_executor.py:438）随样本落盘请求参数快照——`{thinking 档位, tools_fp, reasoning_chars, messages 前缀指纹}`（只进 cache_metrics.jsonl，不进模型面、零缓存影响）。两个用途：
1. 钉死 8888 断点 A（跨 turn 首调）/ B（空工具轮）的精确元凶（前缀指纹逐步比对，漂在哪一步一眼可见）；
2. plan_write 上线后提供稳态基线对照——`scripts/cache_hit_report.py` 稳态 ≥95% 口径不变，人工判定、不进 CI 闸（既有裁决）。
