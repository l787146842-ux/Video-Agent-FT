## 决策点 1：摘要指纹怎么算（按什么粒度判断"内容变了没有"）

**现状**：没算指纹——每轮直接重新构建全量状态 JSON 然后塞进去。

**问题**：要做增量方案，必须有一套机制"判断哪些内容变了"。如果按整条状态算（太粗），任何小改动都要重推；如果按每个字段值算（太细），计算量大、对比逻辑复杂。

**参照（dsh）**：别人的做法是按文件级别的 SHA1，每目录有去重键。对应到我们这个项目，合理的粗细度是"按照组/卡来算"。

**选项**：

| 选项 | 粗细度 | 怎么算 | 能检出什么 | 实现难度 |
|---|---|---|---|---|
| A：粗（整个状态一起算） | 整份状态 JSON | `hashlib.sha1(state_json)` | 任何小改动都触发全量重推（最简单粗暴） | 最低 |
| B：中（按组来算）**推荐** | 每组一个指纹（keyElements/shots/audio 下的每张 group card） | `sha1(group_json)`，以组 ID 做键名 | 单组变了只推那个组，其他组不动 | 中 |
| C：细（按卡来算） | 每张草稿卡一张指纹 | `sha1(draft_json)`，以草稿 ID 做键名 | 单卡变了只推那张卡，连 URL 变了也能检出 | 较高 |

**推荐**：**B**（按组算指纹）。理由：裁剪函数 `_apply_stage_profile` 天然就是按组级别做裁剪/摘要的，正好能对上。按卡算虽然更细，但业务上卡变了往往整组也跟着变（组 ID 不变但内部内容变了），按卡算的额外收益不大。

对缓存的键(key)有啥影响：假如按组算指纹，可以在缓存键里加一组有序的(组 ID + 指纹)对，只推有变化的那几个组。

**需要您拍板**：选 A / B / C。

## 决策点 2：增量事件长什么样

**现状**：每轮往对话会话里塞一条带 `source=state` 标记的 user/message 事件，内容是一整份状态 JSON。

**问题**：改成增量方案后，状态事件必须能区分三种情况："第一次（全量基线）"、"内容变了（只推新内容）"、"内容删了（通知移除）"。dsh 的做法就是这三种类型（`changes: set|replace|remove`），放在 `<system-reminder>` 包裹的 user/message 事件里。

**参照（dsh）**：
- 第一次请求 = 一条持久基线消息（用 `<system-reminder>` 包着的工作区指令）
- 之后内容变了 = 带来源标记的附加指令消息（如`Updated instructions from: <path>`+替换内容）
- 内容删了 = 移除通知消息（`Instructions removed: <path>`）
- 路径和指纹都没变的内容绝不重复塞

**选项**：

| 选项 | 长什么样 | 实现 |
|---|---|---|
| A：单事件模式 | 还是每轮一条 user/message 事件，但内容只传变化部分 | 复杂（和"事件就是完整消息"的语义冲突） |
| B：双事件模式——基线与增量分开 **推荐** | 只在首轮/恢复时发一条全量基线，后续轮只推有变化的组（加新/替换/移除） | 对齐 dsh 的搞法（`source=state` 事件加个标记说明是增量，再加个数组列出哪些组变了/哪些删了） |
| C：多事件模式（每组变化一条） | 每增一个组或改一个组就发一条子事件 | 事件数量膨胀，模型收到一堆乱序内容 |

**子决策：增量事件是覆盖型还是积累型？**
- **覆盖型**（推荐）：增量事件 = 该组的完整最新 JSON（不是"改哪里"的补丁/patch）。模型直接拿新内容覆盖旧内容，不需要推理"哪里变了"。对齐 dsh 的"替换内容"风格。
- **积累型**：传"哪里改了"的补丁，让模型自己合并。模型行为更不可控。

**推荐**：**B**，覆盖型。基线的身份标识见决策点 3。

**需要您拍板**：选 A / B / C；如果选 B，确认是覆盖型。

## 决策点 3：第一次的全量基线怎么标识

**现状**：每轮独立构建状态，没有"基线"这个概念。

**问题**：做增量方案必须有个"当前基线版本是多少"的标识，用来：
- 系统恢复或重放时，先重放基线，再把后续的增量一条条叠加上去
- 跨会话（比如写到一半断开重连）时确认基线的版本一致
- 会话历史压缩后，从基线+增量重新推导当前状态

**参照（dsh）**：基线消息是持久化的，重放时不重复发。每条指令消息带 `version`/`digest`/`identity` 标识。如果可见基线匹配，恢复时复用那条持久消息——这是跨轮缓存命中的关键。

**选项**：

| 选项 | 什么时候发基线 | 用啥做标识 |
|---|---|---|
| A：基线和首轮状态事件合在一起 **推荐** | 会话的第一条 `source=state` 事件就是基线（全量），之后的事件只推增量 | 这条基线事件自身的 event_id 或序列号就是身份 |
| B：基线和状态内容分开 **推荐** | 首轮 `source=state` 事件之前先发一条独立的轻量基线标识（只含版本号和摘要）；真正的状态内容在 state 事件里 | 版本号 = 所有组 ID+指纹 的拼接后的 SHA1 |
| C：前端同步时重建基线 | 只在首轮或者分叉回退时发一次基线和全量状态；后面按增量走 | 不发单独的基线标识事件 |

**恢复场景**：会话断线重连恢复时，从头重放会话日志 → 遇到基线事件 → 重建"当前状态快照"= 基线全量 + 按顺序应用所有增量事件（新增/替换/移除）。这个逻辑和现有 append-only 重放是一回事。

压缩场景：会话历史压缩（compaction）对老轮组操作后，被收编的状态事件（含基线）进入压缩摘要中。压缩点之后的事件继续按增量走。恢复时：压缩摘要里的状态不能再单条还原，但压缩点之后的增量链是完整的。

**推荐**：**A**（基线和首轮状态事件合一，事件自身序号就是标识）。理由：简单，不需要多引入一个独立的基线标识事件（选 B 会多一次来回）；压缩后也不需要重建基线摘要（因为被压缩的状态事件等价于一段已经合并的历史）。

**需要您拍板**：选 A / B / C。

## 决策点 4：老状态块怎么处理

**现状**：会话历史压缩（`session_log.compact_pass`）本身就是按阈值自动做摘要的。老的状态事件（`source=state`）就是普通的 user/message 事件，跟着老轮组一起被压缩收编。

**问题**：改成增量方案后，如果每轮只推几个有变化的组（增量很小），状态事件不一定会触发压缩阈值——那就不用额外处理。但推论：轮次很多之后，增量事件链条变得很长，重放时得一条条叠加 → 开销虽小但线性增长。dsh 的做法是：设一个字节预算，超预算就省略比较粗的文件、截断最具体的文件，超预算的文件视为暂时不可用而非被移除。

对应到我们的约束：状态事件也有 `state_context_budget_chars`（20000 字）的预算（现有的 A/B 档降级链）。改成增量不改变这个预算，但全量 JSON 变成只推几 K 的变化 → 预算压力大幅降低。

需不需要专门写个"收编老状态增量链"的 pass？方案：正常的压缩（阈值=窗口的 80%）自动处理——增量事件链条被压缩时，用 `replaces_seqs` 折叠——**不需要专门的 pass**。

一个例外：恢复时。如果基线事件已经被压缩收编（进了压缩摘要），那增量链在压缩块之后继续。恢复流程：
1. 从会话日志重放到压缩标志 → 识别压缩边界
2. 重建时：压缩摘要里的状态内容（不是 JSON 了）→ 跳过；从压缩点之后的增量事件链条开始
3. 所以增量链需要能在压缩点"续着跑"，而不是从头开始应用

在这个场景下，当基线被压缩时，压缩块之后的第一个状态事件应该**退化成该轮的全量快照**，作为新的基线（reset 原点）。后面的增量链继续叠加。

**选项**：

| 选项 | 行为 |
|---|---|
| A：不专门处理 **推荐** | 正常压缩自动处理；被压缩的状态增量链自然折叠；压缩后第一条状态事件变回全量（当断点基线） |
| B：专门写个状态收编通道 | 另写一套压缩逻辑确保状态块始终可读（额外复杂度，收益有限） |

**推荐**：**A**。理由：现有 append-only 的压缩已经支持 `replaces_seqs` 折叠 + 检查点续跑。把状态增量链当普通事件链处理，压缩点退化成全量是自然的"即使挂了也能工作"的设计。

**需要您拍板**：选 A / B。

## 决策点 5：缓存键要不要重新设计

**现状**：`context_builder.py:77` 的缓存键 = `f"{asset_mode}:{stage or '-'}:{scope_key}"`。

**问题**：缓存键里包含 `stage`。改成增量方案后：
- 如果每次增量不影响状态内容（没有组变化），但 stage 不变（一直都是"structure"），那缓存键不变，命中率高。
- 如果增量导致组变了（比如 key_elements 新增一组），缓存自然就失效了（state_manager 会清空状态缓存）。
- 但增量方案想利用"状态没变就不重复塞事件"——这个判断不在缓存键里，而是在 `planner._build_and_log_state_event`（每轮开始构建之前先检查指纹有没有变化）。

结论：**缓存键可以保持不变**，因为它缓存的是"状态 JSON 的构建结果"（由 state_manager 的清空机制驱动），不是"增量对账"的缓存。

增量对账的关键机制是：**在往模型塞状态事件之前，比一下这轮的状态指纹和上一轮是不是一样**：
- 完全一样 → 不塞 state 事件（模型上下文完全不变，省掉一整个事件的 token 开销）
- 有变化 → 只塞有变化的组

这个"指纹比较器"是新组件，和缓存键体系没关系。

**选项**：

| 选项 | 方式 | 命中率影响 |
|---|---|---|
| A：保留现有缓存键，新增指纹比较器 **推荐** | 缓存键不变（三维度）；指纹比较器按决策点 1 的结论做组级比对 | 状态真没变时完全省一轮事件（最优） |
| B：把指纹也塞进缓存键 | 缓存键包含指纹，指纹没变就命中缓存（不需要重新构建状态 JSON） | 能省状态 JSON 构建的 CPU（但构建本身成本很低 ~2ms）；而且会让缓存失效更频繁（任何组变了缓存都不命中，包括不含状态内容的小变化——可能反倒退步） |

**推荐**：**A**。新增一个指纹比较器（放 `planner` 的轮始函数里或者放 `_build_and_log_state_event` 里），在构建状态 JSON 之前先检查。如果状态没变 → 跳过本次注入（返回一个特殊标记，让轮首不追加 state 事件）。如果变了 → 构建 JSON + 只注入变化组 + 写日志。

**需要您拍板**：选 A / B。

## 决策点 6：要不要保留"每轮全量"的回滚开关

**现状**：已经有 `state_context_budget_chars`（设为 0 = 永远不裁剪预算，全量注入）作为回滚开关。

**问题**：改成增量方案后，需要同样有逃生出口——万一增量逻辑出 bug 或者模型表现不对劲，能一键切回"每轮全量"的老模式。

**选项**：

| 选项 | 开关形式 | 默认值 |
|---|---|---|
| A：一个全局开关 **推荐** | 新增 `state_delta_enabled` 设置项（存在 `runtime_settings.json` 里，热生效）；True=走增量，False=走全量（现在这样） | `False`（默认全量保保守）或 `True`（主动推进增量） |
| B：用 `state_delta_budget_chars=0` 表示关闭 | 复用现有 `state_context_budget_chars` 的语义（0=全量） | 不用新增字段，但逻辑上会搞混 |

**选项 A 推荐**。理由：
- 您拍板之后 `state_delta_enabled=True` 为默认开（主动采用新行为）。
- 万一增量方案出问题 → 在运行设置页或环境变量设 `STATE_DELTA_ENABLED=false` → 重启或热切换即刻生效。
- 清理时：`state_delta_enabled` 归 `RuntimeSettingsUpdate` 路由（"agent" 白名单组）。

**附：子决策**——增量处理失败的兜底
- 增量构建或写日志异常 → 自动回退为全量（和 G3 的"退化保险丝"同样逻辑：`build_agent_context` 失败就降级）。
- 增量指纹比较器抛异常 → 回退全量，记录审计日志。

**需要您拍板**：选 A / B；如果选 A，初始默认值设什么（建议 True，主动推进增量）？
